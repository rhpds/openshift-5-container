= Module 4: Agentic Data-Path Investigation — Healthy Pods, Broken Parks
:navtitle: Agentic Data-Path Investigation
:page-toclevels: 2
:experimental:

In Module 3 you fixed a *readiness probe* through student Gitea and proved the new ParksMap revision rolled out. You now have two independent, working National Parks applications.

Module 4 introduces a different incident: *the Python backend appears healthy, the ParksMap frontend loads, and MongoDB is Running, but the API can no longer return park records*. You will introduce one wrong database hostname in the *GitOps-managed backend* and investigate the difference between Kubernetes health and a real, working application. You will use Lightspeed, inspect an optional instructor-led analysis-only AgenticRun, then *repair the configuration through Git*.

This follows the same controlled, student-owned, evidence-first pattern as xref:module-03-agentic-application-operations.adoc[Module 3] and is adapted from https://rhpds.github.io/ocp5-first-look-lab/modules/module-01-agentic-troubleshooting.html[the OpenShift 5 First Look Agentic Troubleshooting lab]. No production-wide alert policy changes, auto-remediation or cluster-admin student privileges are required.

*Estimated duration: 40 minutes.*

[cols="1,3",options="header"]
|===
| Time | Mission
| 6 min | 1 — Verify both National Parks stacks and record an end-to-end API baseline.
| 7 min | 2 — Introduce a wrong MongoDB Service hostname in student Gitea and observe Auto-Sync.
| 9 min | 3 — Troubleshoot the data path with Lightspeed and independent Kubernetes evidence.
| 10 min | 4 — Examine a real analysis-only AgenticRun or a documented permission-based fallback.
| 8 min | 5 — Remove the faulty override through Gitea and prove full application recovery.
|===

== Learning objectives

* Distinguish *Pod readiness*, *Argo CD health* and *application-level data availability*.
* Understand how Kubernetes explicit +env+ values override values imported with +envFrom+.
* Investigate a misspelled Service hostname without reading MongoDB credentials or mutating the live workload.
* Verify the difference between a valid MongoDB Service and an application configured to use a non-existent Service.
* Compare Lightspeed Troubleshooting with an optional persisted +AgenticRun+ and the human approval boundary.
* Recover an incident through Gitea and prove that the *original* application in +{user}-demo+ was unaffected.

[IMPORTANT]
.Safe student boundary
====
Only change the *student-owned* Gitea +main+ copy of
+content/modules/ROOT/examples/module02-gitops/fullstack/02-nationalparks-backend.yaml+.

* The affected application is in +{user}-gitops+. The *original* +{user}-demo+ application must continue to work.
* Do not change MongoDB, Secret values, PVCs, storage, CPU/memory limits, the Route, Service names, shared tenant quotas, cluster-wide alert routing or +ApprovalPolicy+.
* Do not run +oc patch+, +oc set env+, +oc apply+, +oc delete+ or +oc scale+ against the workload for this exercise. Gitea is the source of truth.
* Do not invoke the +/ws/data/load+ endpoint during the incident: it can delete and reload the database collection, and loading data cannot repair a wrong hostname.
* Restore the known-good manifest *before* moving to Module 5.
====

[NOTE]
.Important Agentic prerequisite
====
A working OpenShift MCP server and Lightspeed chat are *not evidence* that the Agentic Operator, +AgenticRun+ console plug-in or +oc agentic+ CLI is available to a student. +AgenticRun+ CRDs can exist while students cannot create or read resources in +openshift-lightspeed+.

Missions 1, 2, 3 and 5 use normal student permissions and GitOps. Mission 4 is a single *instructor-led, analysis-only* run when the agentic integration is ready; otherwise complete the same evidence-based comparison using Lightspeed and +oc+. Do not expand student RBAC to make a demonstration work.
====

== Mission 1: Capture a real data-path baseline (6 minutes)

A working Kubernetes readiness check does *not* guarantee a database-backed endpoint works. Verify what users actually receive *before* changing anything.

. Capture Routes and responses:
+
[source,bash,role=execute]
----
export MAP_HOST="$(oc get route parksmap -n "$GITOPS_NAMESPACE" -o jsonpath='{.spec.host}')"
export API_HOST="$(oc get route national-parks-app -n "$GITOPS_NAMESPACE" -o jsonpath='{.spec.host}')"

curl -sS -o /dev/null -w 'ParksMap HTTP %{http_code}\n' "https://$MAP_HOST/"
curl -sS -o /dev/null -w 'Backend health HTTP %{http_code}\n' \
  "https://$API_HOST/ws/healthz/"
curl -sS -o /dev/null -w 'Park data HTTP %{http_code}\n' \
  "https://$API_HOST/ws/data/all"
----
+
*Expected:* successful responses from all three endpoints (normally HTTP 200).
+
image::module04-s01-healthy-api-routes.svg[S01: Check all API routes first - screenshot placeholder, width=850]

. Check that the API returns *actual records*, not merely HTTP 200:
+
[source,bash,role=execute]
----
curl -fsS --max-time 25 "https://$API_HOST/ws/data/all" | \
  python3 -c 'import json,sys; data=json.load(sys.stdin); assert isinstance(data,list); print("Park records:",len(data)); assert len(data)>0'
----
+
A prepared workshop database usually has thousands of records. Do not seed the database again if records already exist.
+
image::module04-s02-parks-record-count.svg[S02: Confirm real park data - screenshot placeholder, width=850]

. Check the backend's expected config without reading the Secret:
+
[source,bash,role=execute]
----
oc get deployment nationalparks -n "$GITOPS_NAMESPACE" -o json | \
  jq '{envFrom: .spec.template.spec.containers[0].envFrom,
       explicitEnv: .spec.template.spec.containers[0].env}'
oc get service mongodb-nationalparks -n "$GITOPS_NAMESPACE" \
  -o custom-columns='NAME:.metadata.name,PORT:.spec.ports[0].port,TARGET:.spec.ports[0].targetPort'
oc get deploy mongodb-nationalparks nationalparks parksmap -n "$LAB_NAMESPACE"
----
+
In the known-good GitOps source, the backend uses +envFrom.secretRef+ to load the database configuration; it has *no explicit* +DATABASE_SERVICE_NAME+ override. The Service name is +mongodb-nationalparks+ (without an extra hyphen). The original application is still healthy.

*Checkpoint 1:* Both application stacks are healthy, ParksMap and API Route work, and +/ws/data/all+ returns park records.

*Predict:* Can a backend return HTTP 200 from +/ws/healthz/+ while a database query fails?

[%collapsible]
====
*Answer:* Yes. This National Parks Python backend's health endpoint returns a simple +OK+ JSON response and does not access MongoDB. A DNS or database connection failure can therefore break the data path without immediately failing the readiness probe.
====

== Mission 2: Deploy the wrong database hostname through Gitea (7 minutes)

The incident is a realistic configuration regression: a release introduces an *explicit environment-variable override* with a misspelled database hostname.

Kubernetes loads the correct +DATABASE_SERVICE_NAME+ from the existing MongoDB Secret through +envFrom+, but an entry with the same name in explicit +env+ takes precedence. We will add *only* that one wrong value. The Secret, MongoDB data and Service remain intact.

. Open your own student Gitea repository +{user}/openshift-5-container+, select branch +main+, and navigate to:
+
[source,text,role=copypaste]
----
content/modules/ROOT/examples/module02-gitops/fullstack/02-nationalparks-backend.yaml
----
+
Locate the +Deployment+ for +nationalparks+, inside +spec.template.spec.containers+ under +name: nationalparks+. Do *not* change the BuildConfig or ImageStream in the same file.
+
image::module04-s03-gitea-backend-source.svg[S03: Locate the Python Deployment - screenshot placeholder, width=850]

. Find the existing block:
+
[source,yaml,role=copypaste]
----
          envFrom:
            - secretRef:
                name: nationalparks-mongodb-parameters
          readinessProbe:
----
+
Insert the additional +env+ block between +envFrom+ and +readinessProbe+:
+
[source,yaml,role=copypaste]
----
          envFrom:
            - secretRef:
                name: nationalparks-mongodb-parameters
          env:
            - name: DATABASE_SERVICE_NAME
              value: mongodb-national-parks
          readinessProbe:
----
+
The broken value is +mongodb-national-parks+ (extra hyphen). The *real* Service is +mongodb-nationalparks+. Leave the rest of the Deployment unchanged, including the existing limits and health checks.
+
image::module04-s04-gitea-wrong-db-host.svg[S04: Inject bad MongoDB hostname - screenshot placeholder, width=850]

. Commit to your student Gitea +main+ branch:
+
[source,text,role=copypaste]
----
lab(module04): simulate National Parks database DNS misconfiguration
----
+
Open *GitOps → Applications → national-parks-settings* (project +{user}-demo+) and watch the source revision update. Auto-Sync is already enabled. *Do not manually Sync.*
+
image::module04-s05-gitea-commit-and-argocd.svg[S05: Commit and watch Auto-Sync - screenshot placeholder, width=850]

. Inspect the actual live configuration and rollout:
+
[source,bash,role=execute]
----
oc get application "$ARGOCD_APP" -n "$ARGOCD_NAMESPACE" -o json | jq '{
  sync: .status.sync.status,
  health: .status.health.status,
  revision: .status.sync.revision
}'

oc get deployment nationalparks -n "$GITOPS_NAMESPACE" -o json | jq '{
  envFrom: .spec.template.spec.containers[0].envFrom,
  explicitEnv: .spec.template.spec.containers[0].env,
  readiness: .spec.template.spec.containers[0].readinessProbe
}'

oc get deploy mongodb-nationalparks nationalparks parksmap -n "$GITOPS_NAMESPACE"
oc get service mongodb-nationalparks -n "$GITOPS_NAMESPACE"
----
+
The live +nationalparks+ Deployment must contain the explicit *wrong* value. The Deployments may *still* report *1/1 Ready*, and Argo CD may settle at *Synced / Healthy*, because this app's readiness probe does not exercise MongoDB. A sustained stream of failing data requests could also occupy workers and cause intermittent readiness failures; report the *actual* state rather than assuming it.

. Demonstrate the broken data path. Use a timeout so DNS/MongoDB client retries do not hold your terminal indefinitely:
+
[source,bash,role=execute]
----
curl -sS --connect-timeout 5 --max-time 15 \
  -o /dev/null -w 'Backend health HTTP %{http_code}\n' \
  "https://$API_HOST/ws/healthz/"

curl -sS --connect-timeout 5 --max-time 15 \
  -o /dev/null -w 'Park data HTTP %{http_code}\n' \
  "https://$API_HOST/ws/data/all" || \
  echo "Park data request timed out or failed — record the error."
----
+
*Expected:* the health endpoint may still return 200 while the data endpoint times out or produces an error. Do not demand an exact HTTP status: PyMongo connection selection and web worker timing can vary. If data still returns a non-empty array, confirm the *new* Deployment revision has rolled out before concluding the fault had no effect.
+
image::module04-s06-healthy-pods-broken-data.svg[S06: Healthy Pods, failed data request - screenshot placeholder, width=850]

*Checkpoint 2:* Your bad Gitea commit is live, the Python backend has +DATABASE_SERVICE_NAME=mongodb-national-parks+ explicitly configured, MongoDB remains healthy, and the API data path no longer returns records successfully.

== Mission 3: Investigate with Lightspeed and Kubernetes evidence (9 minutes)

The important question is not "Is Kubernetes green?" but *"Why is the backend resolving the wrong host?"*

. Open *OpenShift Lightspeed → Troubleshooting* in the OpenShift 5 console. Use this prompt, replacing the namespace if your console does not expand the student placeholder:
+
[source,text,role=copypaste,subs="attributes+"]
----
Investigate a National Parks application data-path incident
in namespace {user}-gitops.

The ParksMap frontend loads and the MongoDB Pod is Running.
The nationalparks backend health probe may still be passing,
but /ws/data/all no longer returns park records after a new
student Gitea GitOps revision.

Use available live, read-only tools to:
1. Check Deployment/nationalparks and the new Pod's status,
   readiness probe, and recent logs;
2. Inspect only non-sensitive explicit environment values
   and envFrom reference names (do not read Secret data);
3. Compare the configured MongoDB hostname with the
   actual Service names and ports in this namespace;
4. Check GitOps Application national-parks-settings
   in {user}-demo if your tools permit it;
5. Explain why Synced / Healthy may coexist with a broken
   database-backed API endpoint.

Identify tool evidence versus assumptions and propose
the smallest change in the student Gitea manifest.
Do not execute, patch, scale, create or delete anything.
Do not read Secrets or access other student namespaces.
----
+
If Lightspeed cannot query the cluster, it must say so. Do not treat generic AI knowledge as evidence or approve any mutating tool call.
+
image::module04-s07-lightspeed-data-path-prompt.svg[S07: Ask Lightspeed to investigate - screenshot placeholder, width=850]

. Inspect the *same* fields yourself:
+
[source,bash,role=execute]
----
oc get deployment nationalparks -n "$GITOPS_NAMESPACE" -o json | \
  jq '.spec.template.spec.containers[0] |
      {envFrom, explicitEnv: .env, readinessProbe}'

oc get service mongodb-nationalparks -n "$GITOPS_NAMESPACE" -o yaml | \
  sed -n '/^metadata:/,/^status:/p'

oc get services -n "$GITOPS_NAMESPACE"
oc logs deployment/nationalparks -n "$GITOPS_NAMESPACE" --tail=70 --timestamps
----
+
You should be able to demonstrate the *wrong hostname from the Deployment YAML*, the *correct Service name from the Kubernetes API*, and, after a failing data request, a DNS or MongoDB server-selection error in logs. The specific Python exception can vary.
+
image::module04-s08-backend-env-vs-mongodb-service.svg[S08: Compare env and real Service - screenshot placeholder, width=850]

. If your student role permits Pod execution, try *read-only DNS checks* from the running backend Pod; otherwise skip this step without escalating privileges:
+
[source,bash,role=execute]
----
if oc auth can-i create pods/exec -n "$GITOPS_NAMESPACE" | grep -qx yes; then
  POD="$(oc get pods -n "$GITOPS_NAMESPACE" -l app=nationalparks \
    -o jsonpath='{.items[0].metadata.name}')"
  if [ -n "$POD" ]; then
    oc exec -n "$GITOPS_NAMESPACE" "$POD" -- \
      python3 -c 'import socket; print(socket.getaddrinfo("mongodb-nationalparks",27017)[0][4][0])'
    oc exec -n "$GITOPS_NAMESPACE" "$POD" -- \
      python3 -c 'import socket; print(socket.getaddrinfo("mongodb-national-parks",27017)[0][4][0])' \
      || echo "Wrong hostname does not resolve — expected."
  fi
else
  echo "Pod exec not authorized. Deployment and Service evidence are sufficient."
fi
----
+
The correct name should resolve; the wrong one should fail. Do not create temporary DNS pods in a shared quota-constrained tenant. The *netedge* MCP toolset is optional; do not assume it exists or claim it executed DNS checks unless its tool output proves it.
+
image::module04-s09-dns-and-backend-log-evidence.svg[S09: Corroborate the DNS failure - screenshot placeholder, width=850]

. Ask Lightspeed to challenge its own hypothesis:
+
[source,text,role=copypaste,subs="attributes+"]
----
Prove which DATABASE_SERVICE_NAME value the backend will
actually use. Kubernetes imports environment variables from
a Secret via envFrom, but the Deployment also contains an
explicit env value with the same key. Which wins, and which
live field confirms it? Explain the smallest source-controlled
repair without accessing the Secret or making any changes.
----

A correct answer identifies *the explicit override* and the real Service, not a request to change MongoDB passwords, create a DNS record, relax NetworkPolicy or increase resource limits. Kubernetes explicit +env+ overrides duplicate +envFrom+ keys.
+
image::module04-s10-lightspeed-db-root-cause.svg[S10: Check the AI's root cause - screenshot placeholder, width=850] 

*Checkpoint 3:* You can explain the wrong Service name, its precedence over the imported correct value, and the distinction between health checks and real data availability.

*Predict:* Why is changing the MongoDB Service itself the wrong repair?

[%collapsible]
====
*Answer:* The Service name is correct, and both the original app and GitOps stack depend on their intended namespace-local Services. The regression was introduced in the *backend container's explicit environment configuration*, so removing that override restores its original, correctly generated setting without disrupting storage or other workloads.
====

== Troubleshooting

[cols="2,3",options="header"]
|===
| Symptom | What to check
| The changed Gitea file does not update the Deployment | Confirm student-owned +main+, the correct +fullstack/02-nationalparks-backend.yaml+ file, the Argo CD source revision and Auto-Sync. Changes to upstream GitHub do not automatically update Gitea.
| +Synced / Healthy+ even though data is broken | Expected: this API's readiness handler does not query MongoDB. Query +/ws/data/all+ and inspect logs and the explicit +env+ override.
| The override has not taken effect | Inspect the new Pod's revision/age and Deployment +env+ list. Do not edit the Secret to force the fault.
| Wrong-name DNS lookup blocked by RBAC | Use the Deployment's non-sensitive explicit +env+ value and the actual Service list. Pod exec is optional, not permission to escalate.
| API data query times out rather than returning 500 | PyMongo server-selection retries and Gunicorn worker timeouts can vary. Record the real HTTP/curl result; inspect backend logs without looping high request rates.
| AI reports the wrong namespace or guessed output | Stop trusting that finding and use live +oc+ evidence. Only the student's +{user}-gitops+ workload is in scope.
| +AgenticRun+ returns Forbidden | Normal student isolation. The instructor can demonstrate a single analysis-only run; no cluster-wide approval or RBAC change is justified.
| Recovery commit applied but old error persists | Confirm live explicit +env+ is gone, then verify the repaired Pod is running. Review the current and old Argo CD sync operations; do not delete Secrets/PVCs.
| ParksMap HTTP 200 but no markers after repair | Test +/ws/data/all+ and +/ws/backends/list+, refresh the browser and verify National Parks (PY) layer; do not reload data unless the collection is truly empty and instructor approves.
|===
