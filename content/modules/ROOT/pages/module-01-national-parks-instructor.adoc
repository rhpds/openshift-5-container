=== Required Student-Identity Preflight

Perform these *before* the session, using at least two actual student identities rather than only `cluster-admin`:

* Confirm the precise OpenShift 5 UI navigation and scaling control shown in the screenshot placeholders. OpenShift 4.19 and later use a unified console by default; do not require learners to switch to a legacy Developer perspective.
* Ensure every student project has an initialized `national-parks-app`: `parksmap` at *1 desired / 1 ready*, ready backend/database, admitted HTTPS Routes, a working map, and nonempty `/ws/data/all`.
* Check `oc auth can-i update deployments/scale -n {lab_user}` with the student token. Keep the permission namespace-scoped and limited to the intended exercise; verify reads for Routes, Services, EndpointSlices, Pods and logs separately.
* Rehearse the complete *1 → 2 → 1* change in the **UI**. An HPA, Argo CD self-heal, or another reconciler must not immediately undo the scale exercise. Decide and document GitOps ownership behaviour before class, then return the Deployment to its source-of-truth state.
* Verify the Route remains reachable and EndpointSlices reflect the new ready pod after scaling. If the second pod fails to become ready within about 90 seconds, use a per-student reset/recovery path, not shared-cluster edits.
* Verify the built-in Lightspeed/MCP **read** path as the student: successful tool calls and results on that namespace, no access to other students' resources or Secrets. The model's prose alone is not proof. If live tool inspection is unavailable, tell the class to use the documented CLI result classification.

== Confirm the Release and Feature Scope

OpenShift 5.0 documents Kubernetes 1.36 with CRI-O, general availability of the MCP server for Red Hat OpenShift, HAProxy 3.2 as the ingress default with a 2.8 migration option, and project-scoped credentials for mirrored registries. The new agentic Cluster Update assessment remains Technology Preview and requires the Lightspeed Agentic Operator.

Check the cluster's actual release as an administrator:

[source,bash]
----
oc get clusterversion version
----

Record the completed release and the `Available` and `Progressing` conditions. Then check the reported Kubernetes server version:

[source,bash]
----
oc version
----

The repository still configures the last supplied workshop build, `{ocp_version}`. Update that attribute only when it matches the environment you provision. Publishing the documentation or refreshing the guide does not upgrade the cluster or its installed add-ons.

MCP server GA does not make every optional toolset, installation method, or Lightspeed integration GA. Record the installed operator and server versions, verify their compatibility, and check their own support status before describing the workshop environment as a GA deployment.

== Application Contract

Provision one application instance in each participant's assigned namespace, `{lab_user}`. The existing workshop bootstrap creates that namespace and delegates access to the participant's Showroom service account. The index displays the participant's credentials, and Module 1 derives the application namespace from either the username or `system:serviceaccount:<student>-showroom:<service-account>` identity. Populate the Showroom attributes and verify that this naming convention produces the assigned application namespace. An administrator rehearsing another student's environment must select that namespace explicitly.

[cols="2,3",options="header"]
|===
| Resource | Required behaviour
| `Deployment/parksmap` | Frontend image tested on the workshop build; Service discovery permissions; one or more Ready pods.
| `Service/parksmap` | Selects the frontend pods and targets their listening port.
| `Route/parksmap` | Admitted HTTPS Route to the frontend Service, with a hostname and certificate trusted by the student terminal and browser.
| `Deployment/nationalparks` | Tested Python backend image, database connection provided through Secret references, and one or more Ready pods.
| `Service/nationalparks` | Selects backend pods and targets their listening port, normally `8080` for the documented Python application.
| `Route/nationalparks` | Admitted HTTPS Route with the discovery label `type=parksmap-backend`.
| `Deployment/mongodb-nationalparks` | Database image, initialization, credentials, storage, and permissions tested as a compatible combination.
| `Service/mongodb-nationalparks` | Internal database access on the port configured in the backend, normally `27017`.
| Application labels | Set `app.kubernetes.io/part-of=national-parks-app` on all three workload objects and pod templates. Also set `component=parksmap`, `component=nationalparks`, or `component=mongodb-nationalparks` on the respective pods.
| Initialized data | `/ws/data/all` returns a non-empty JSON array and park markers are visible in the frontend.
|===

Use `apps/v1` Deployments for this workshop contract. If an existing database deployment uses a StatefulSet, adapt the explicit database checks in the guide to that verified deployment before delivery.

== Images, Credentials, and Application Discovery

The 5.0 tutorial uses:

* Frontend example image: `quay.io/openshiftroadshow/parksmap:latest`.
* Backend source: https://github.com/openshift-roadshow/nationalparks-py[openshift-roadshow/nationalparks-py].
* Database example image: `registry.redhat.io/rhmap47/mongodb`.

Treat these as tutorial references, not a tested image bill of materials. Build or select the images you will deliver, rehearse them on the target architecture and OpenShift build, and record immutable image digests in the deployment configuration. Supply registry credentials or mirrors where required.

The reviewed database documentation still contains an inconsistency between its command's image reference and its sample output. Confirm your chosen image's environment variables, volume paths, initialization method, and arbitrary-UID behaviour. Substituting a different MongoDB image can require different initialization settings.

The reviewed Python backend at https://github.com/openshift-roadshow/nationalparks-py/tree/72d12d95494e2bdf67e859a7db8b224cba0e0daa[commit 72d12d9] uses Python 3.12, Flask, gunicorn, and PyMongo. Its README describes the database environment variables and endpoint paths. Pin the source and builder versions when building it; a floating builder selection is not a reproducible workshop build.

Use a dedicated frontend service account for route/service discovery and namespace-scoped access. The upstream tutorial demonstrates the namespace `view` role; a narrower role is appropriate once its required reads have been verified. Avoid granting that discovery access to every workload through the default service account.

Provide database settings to the backend through Secret references. The reviewed backend accepts `DATABASE_SERVICE_NAME` or `MONGODB_SERVER_HOST`, plus the documented user, password, port, and database fields. Use generated workshop credentials rather than copying the tutorial's example password.

The frontend needs access to the backend route, its configured discovery API, and any map assets. The backend needs DNS and database access. Check these paths against existing policies before the student session. Keep MongoDB internal.

=== Optional Mirrored-Registry Demonstration

The 5.0 Images guide documents project-scoped pull secrets for mirrored registries. This requires the administrator to configure `CRIOCredentialProviderConfig/cluster` with `spec.matchImages`, provide the namespace's registry secret, and configure the pod service account's required access. Merely creating a conventional pull secret or pulling a public image does not demonstrate this feature.

If you have prepared a mirror demonstration, inspect the configured registry matches without reading any credentials:

[source,bash]
----
oc get criocredentialproviderconfigs.config.openshift.io cluster \
  -o jsonpath='{.spec.matchImages}{"\n"}'
----

Verify the mirror, credential-provider configuration, namespace, service account, and successful image pull during preparation. A Deployment's requested image reference alone cannot identify the registry that actually served the image. If the API or configuration is absent in the installed build, keep this as a documented release topic and use the core image-inventory exercise.

== Provision Through the Intended GitOps Owner

Use a dedicated application directory and Application for National Parks, such as `apps/national-parks`, or the equivalent path in your existing repository. This is a suggested convention, not a path already created by this revision.

Commit the tested Deployments, Services, Routes, application labels, and non-secret configuration to the intended Git repository. Deliver Secrets through the workshop's credential mechanism. Let that Application own the application resources from the beginning so later GitOps exercises do not have to adopt resources created by an unrelated workflow.

Complete image builds before the timed student lab. If the chosen deployment also uses BuildConfigs or ImageStreams, identify who owns them and how image changes are reconciled. Avoid competing image triggers and GitOps image updates.

Initialize the database once during setup using the tutorial's load operation. In the reviewed backend, `/ws/data/load` deletes and reloads the collection. Never use it as a health check or call it during the student inspection exercises. The example exposes this mutating operation through the backend service, so use only disposable workshop data and apply the workshop's intended access restrictions.

== Verify the Student Experience

Run these checks while authenticated as an actual student or Showroom identity. Use the participant's application namespace, not the namespace hosting the terminal.

[source,bash]
----
printf 'Application namespace to rehearse: '
read -r LAB_NAMESPACE
: "${LAB_NAMESPACE:?An application namespace is required}"

for deployment in parksmap nationalparks mongodb-nationalparks; do
  oc rollout status deployment/"$deployment" \
    -n "$LAB_NAMESPACE" --timeout=180s
done

oc get pods -n "$LAB_NAMESPACE" \
  -l app.kubernetes.io/part-of=national-parks-app -o wide
oc get services parksmap nationalparks mongodb-nationalparks -n "$LAB_NAMESPACE"
oc get routes parksmap nationalparks -n "$LAB_NAMESPACE"
oc get route nationalparks -n "$LAB_NAMESPACE" \
  -o jsonpath='backend discovery label={.metadata.labels.type}{"\n"}'
oc get endpointslices.discovery.k8s.io -n "$LAB_NAMESPACE" \
  -l kubernetes.io/service-name=parksmap
oc auth can-i get pods --subresource=log -n "$LAB_NAMESPACE"
oc adm top pods -n "$LAB_NAMESPACE" \
  -l app.kubernetes.io/part-of=national-parks-app --containers
----

Verify all of the following before opening the class:

* Both application Routes are admitted and use the HTTPS configuration assumed by the student commands.
* The frontend returns HTTP `200`; the map displays park markers.
* `/ws/healthz/` responds successfully and `/ws/data/all` returns a positive record count.
* The frontend EndpointSlices identify ready pods.
* Logs and metrics can be read with the student identity, or the instructor announces the documented fallback.
* Pod labels support both selectors used in the module.
* Shared namespace services such as Argo CD or Gitea are excluded from the application selector.

The health handler in the reviewed backend returns `OK` without querying MongoDB. A meaningful readiness configuration can include additional checks, but the student module deliberately verifies the data path separately.

== Configure and Rehearse the AI Path

The core student exercise uses Lightspeed's built-in MCP resource tools. It does not require a custom MCP server, the `netedge` toolset, or the MCP Gateway Operator.

The 5.0 AI applications guide also documents a gateway-managed installation path involving an MCP gateway and the MCP Lifecycle Operator. That lifecycle procedure is explicitly Technology Preview and references an OpenShift AI Early Release dependency. It is a separate deployment path, not a repair step for the already functioning Lightspeed connection shown below. Follow the matching component documentation if you choose that architecture.

The operator's installed CRD and the {lightspeed-config}[Lightspeed configuration guide] are the configuration references. Do not apply an earlier preview's schema without checking `oc explain` on the target cluster.

=== Optional Streaming API Check

Use two terminal sessions for this rehearsal. In terminal A, keep the instructor-authorized loopback port-forward running:

[source,bash]
----
oc -n openshift-lightspeed port-forward --address 127.0.0.1 \
  deployment/lightspeed-app-server 18443:8443
----

In terminal B, use a token-based login for the student being tested and confirm its identity:

[source,bash]
----
oc whoami
----

Select the actual application namespace:

[source,bash]
----
printf 'Enter the student application namespace: '
read -r LAB_NAMESPACE
----

Verify the application Route exists before submitting the AI request. Stop if this fails:

[source,bash]
----
oc get route parksmap -n "${LAB_NAMESPACE:?Enter the application namespace}"
----

Keep the token in a shell variable without printing it:

[source,bash]
----
set +x
OLS_TOKEN=$(oc whoami -t)
: "${OLS_TOKEN:?Use a token-based login for the student identity}"
----

Check query authorization:

[source,bash]
----
curl --insecure --silent --show-error --fail-with-body \
  --connect-timeout 5 --max-time 20 -X POST \
  https://127.0.0.1:18443/authorized \
  -H "Authorization: Bearer $OLS_TOKEN" \
  -w '\nAuthorization HTTP status: %{http_code}\n'
----

Expected: HTTP 200 for the intended identity. This proves query authorization, not successful resource access. Here `--insecure` is limited to the loopback port-forward because the service certificate is not issued to `127.0.0.1`; keep certificate validation enabled for the application's normal Route checks.

Submit a scoped read request:

[source,bash]
----
jq -n --arg ns "${LAB_NAMESPACE:?Select the application namespace}" '{
  query: (
    "Use live MCP read tools in namespace " + $ns + ". " +
    "Read Route parksmap, its target Service, that Service'\''s " +
    "EndpointSlices, and one referenced pod. Report the Route host, " +
    "admission condition, Service, ready endpoint pod names, and pod UID. " +
    "Use only reads in this namespace. Do not read Secrets or execute " +
    "in pods. Report unavailable tools or resources without guessing."
  ),
  media_type: "application/json"
}' | curl --insecure --no-buffer --silent --show-error --fail-with-body \
  --connect-timeout 5 --max-time 120 \
  https://127.0.0.1:18443/v1/streaming_query \
  -H "Authorization: Bearer $OLS_TOKEN" \
  -H 'Content-Type: application/json' --data-binary @-
----

Expected: `tool_call` and `tool_result` events for the actual namespace, followed by a response. Inspect successful result content and compare it with the student CLI observations. A `NotFound` tool result proves the attempted call occurred but does not pass the application check. A `Forbidden` result requires checking the effective identity and permissions.

Clear the token when finished:

[source,bash]
----
unset OLS_TOKEN
----

Stop the port-forward in terminal A with kbd:[Ctrl+C]. See https://docs.redhat.com/en/documentation/red_hat_openshift_lightspeed/1.0/html/operate/ols-interacting-with-the-api[Interacting with the Lightspeed API] for the installed version's API details.

=== Optional netedge Tour

The 5.0 Ingress guide describes the disabled-by-default `netedge` toolset, including `inspect_route` and `get_service_endpoints`. Enable and rehearse it only if demonstrating that optional toolset. Do not infer its availability from successful generic resource reads.

The MCP configuration reference moves runtime settings such as toolset selection and read-only mode into TOML. Its standalone example uses `toolsets = ["core", "config", "netedge"]`; the operator-managed example uses an `MCPServer` resource. These examples describe different deployment methods. Check the installed schema and server documentation before changing configuration; do not apply an `MCPServer` resource to the observed Lightspeed installation, where that API was absent, or copy legacy command-line flags into a newer server.

The guide also lists active tools, including `exec_dns_in_pod`, which can create a scratch pod, and tools that inspect shared router resources. Those operations are outside the student read-only exercise.

If the AI integration is unavailable, announce the CLI fallback before the exercise and label chat interpretation of pasted output as supplied-data analysis. Do not count it as verified live MCP access.

== Verify the Serving Router's HAProxy Version

These are instructor reads of shared ingress resources. Select a ready student's application namespace before running the Route check:

[source,bash]
----
oc get route parksmap -n "${LAB_NAMESPACE:?Select an application namespace}" \
  -o jsonpath='{range .status.ingress[*]}router={.routerName}{" "}{range .conditions[*]}{.type}={.status}{" "}{end}{"\n"}{end}'
----

Find the router reporting `Admitted=True`. Read the configured and effective versions of the IngressControllers:

[source,bash]
----
oc get ingresscontrollers -n openshift-ingress-operator \
  -o custom-columns='NAME:.metadata.name,CONFIGURED:.spec.haproxyVersion,ACTIVE:.status.effectiveHAProxyVersion'
----

Match the Route's `routerName` to the controller's `NAME`. If more than one router admits the Route, verify each relevant controller rather than assuming default serves the request.

The 5.0 documentation defines the fields as follows:

* An omitted `spec.haproxyVersion` selects the release default, HAProxy 3.2 in 5.0.
* Explicit `3.2` pins that version while supported; `2.8` selects the supported migration option.
* `status.effectiveHAProxyVersion` reports the resolved active version, `3.2` or `2.8`. If it is omitted, the Operator has not resolved the version yet.

Record the effective value from the controller serving National Parks. The normal frontend HTTP check verifies the application path, not the router version. Keep version selection changes outside the shared student lab.

== Optional Agentic Update Assessment

The new Administration > Cluster Update assessment is Technology Preview. Before demonstrating it, verify the Lightspeed Agentic Operator is installed and configured, OLS has a working LLM connection, and the presenter has cluster-administrator access. A ready built-in MCP server alone does not satisfy these prerequisites; the author's earlier output reported the agentic console plugin as disabled.

Select a target under *Select Update Path*, choose *Analyse*, and review the resulting assessment. The tool does not execute a cluster update. The documented workflow patches an `AgenticRunApproval`, runs an analysis in a read-only sandbox, and records analysis results. Do not describe the whole assessment workflow as an API-read-only operation or include it in the student read-only MCP exercise.

Use National Parks' successful HTTP and database-backed checks as application evidence alongside the cluster assessment. AI recommendations do not establish application compatibility by themselves. If the integration or an update path is unavailable, discuss the feature without claiming a completed assessment.
