In Module 1 you established that *National Parks* is healthy: the map loads, park markers appear, and the data endpoint returns records.
In this module you will inspect the GitOps configuration that keeps the application in that state, make one declarative change through Argo CD, and verify that both the application and the cluster's access controls behave as expected.

[cols="1,3",options="header"]
|===
| Time | Activity
| 4 minutes | Set context; inspect the Argo CD Application managing National Parks.
| 5 minutes | Clone the GitOps repository and review the application manifests.
| 7 minutes | Add a database NetworkPolicy through GitOps, synchronize, and verify.
| 4 minutes | Verify RBAC isolation between student namespaces.
|===

== Learning Objectives

* Describe how a Git repository, an Argo CD Application, and a namespace fit together.
* Read the synchronization status, health, and deployed revision of a live GitOps-managed application.
* Commit a declarative policy change and observe how Argo CD applies it.
* Verify that the application remains healthy after the policy is enforced.
* Distinguish Kubernetes API isolation (RBAC) from application network isolation (NetworkPolicy).

== OpenShift 5 Connection

[cols="2,3",options="header"]
|===
| Topic | Connection to this module

| OpenShift GitOps operator (OLM v1)
| The Argo CD instance used in this workshop is installed as a `ClusterExtension`. You identified this API in Module 1. The operator lifecycle does not change the Git → cluster synchronization model you use here.

| NetworkPolicy for namespace isolation
| `NetworkPolicy` is a namespace-scoped control applied to selected pods. This module uses it to restrict database access. `AdminNetworkPolicy`, a cluster-scoped alternative managed by the platform team, is separate and may co-exist; your policy is additive to any platform controls already in place.

| RBAC namespace scoping
| A `RoleBinding` in your namespace grants access only within that namespace. This module verifies that the boundary holds against a neighboring student namespace.
|===

NOTE: GitOps, Kubernetes RBAC, and NetworkPolicy are established capabilities used to explore OpenShift 5, not features introduced in this release. Use the installed versions you found in Module 1.

== Exercise 2: Inspect the Argo CD Application (4 Minutes)

The instructor provisioned an Argo CD Application to manage National Parks in your namespace before the workshop. You will read its configuration, not create it.

. Read the Application specification:
+
[source,bash,role=execute]
----
oc get applications.argoproj.io "$ARGOCD_APP" \
  -n "$ARGOCD_NAMESPACE" \
  -o jsonpath='repository={.spec.source.repoURL}{"\n"}branch={.spec.source.targetRevision}{"\n"}path={.spec.source.path}{"\n"}destination={.spec.destination.namespace}{"\n"}project={.spec.project}{"\n"}'
----
+
*Expected:* The repository and branch match what you entered above. The destination matches `$LAB_NAMESPACE`. Record the source path — you will use it when committing your change.

. Check the current synchronization state:
+
[source,bash,role=execute]
----
oc get applications.argoproj.io "$ARGOCD_APP" \
  -n "$ARGOCD_NAMESPACE" \
  -o jsonpath='revision={.status.sync.revision}{"\n"}sync={.status.sync.status}{"\n"}health={.status.health.status}{"\n"}'
----
+
*Expected:* `sync=Synced` and `health=Healthy`. If either is different, note the value but do not attempt to fix it here; the instructor needs to confirm the state before you add a new policy.

. Record the current commit revision:
+
[source,bash,role=execute]
----
CURRENT_REVISION=$(oc get applications.argoproj.io "$ARGOCD_APP" \
  -n "$ARGOCD_NAMESPACE" \
  -o jsonpath='{.status.sync.revision}')
printf 'Current deployed revision: %s\n' "$CURRENT_REVISION"
export CURRENT_REVISION
----
+
This is the baseline. After you commit the NetworkPolicy, you will compare the new revision against this value.

. Open the instructor-provided Argo CD URL in the browser and locate your Application. Note the resource graph — it shows the three National Parks Deployments, their ReplicaSets, pods, Services, and Routes all owned by this Application.

*Checkpoint:* The Application is `Synced` and `Healthy`. You have recorded the baseline revision.

== Exercise 3: Clone and Review the GitOps Manifests (5 Minutes)

. Clone the repository on the branch tracked by Argo CD:
+
[source,bash,role=execute]
----
git clone --branch "$GITOPS_BRANCH" "$GITOPS_REPO_URL" workshop-gitops
cd workshop-gitops
git log --oneline -5
----
+
If the clone already exists from a previous attempt, open it and confirm the branch:
+
[source,bash,role=execute]
----
cd workshop-gitops
git fetch origin
git checkout "$GITOPS_BRANCH"
git pull origin "$GITOPS_BRANCH"
----

. Locate the National Parks manifests using the source path from Exercise 2:
+
[source,bash,role=execute]
----
GITOPS_PATH=$(oc get applications.argoproj.io "$ARGOCD_APP" \
  -n "$ARGOCD_NAMESPACE" \
  -o jsonpath='{.spec.source.path}')
export GITOPS_PATH
printf 'Source path: %s\n' "$GITOPS_PATH"
ls "$GITOPS_PATH/"
----

. Review the Kustomize entry point:
+
[source,bash,role=execute]
----
cat "$GITOPS_PATH/kustomization.yaml"
----
+
Note which resource files are listed. The NetworkPolicy you add will appear here.

. Inspect the Deployment manifests to confirm the pod labels the NetworkPolicy will select:
+
[source,bash,role=execute]
----
grep -r 'component:' "$GITOPS_PATH/" || \
  oc get pods -n "$LAB_NAMESPACE" -l "$APP_SELECTOR" \
    -o jsonpath='{range .items[*]}{.metadata.name}: component={.metadata.labels.component}{"\n"}{end}'
----
+
*Expected:* pods carry a `component` label with values `parksmap`, `nationalparks`, or `mongodb-nationalparks`. The NetworkPolicy in the next exercise uses `component=nationalparks` to select the backend pods as the only permitted source of database traffic.

. Confirm the current state of the application while the repository is still unchanged:
+
[source,bash,role=execute]
----
curl --fail --silent --show-error --connect-timeout 5 --max-time 15 \
  -o /dev/null -w 'Frontend status: %{http_code}\n' "$PARKSMAP_URL/"
curl --fail --silent --show-error --connect-timeout 5 --max-time 15 \
  -w 'Data records: ' "$NATIONALPARKS_URL/ws/data/all" \
  | python3 -c 'import json,sys; d=json.load(sys.stdin); print(len(d))'
----
+
*Expected:* HTTP `200` and a positive record count. This is your before-policy baseline.

*Checkpoint:* You have the repository cloned, the source path confirmed, and a healthy application baseline recorded.

== Exercise 4: Add the MongoDB NetworkPolicy Through GitOps (7 Minutes)

You will restrict database access so that only the `nationalparks` backend pods in your own namespace can reach `mongodb-nationalparks` on port `27017`. No other pod — including pods from another student's namespace — will be able to reach your database.

. Create the NetworkPolicy manifest in the application directory:
+
[source,bash,role=execute]
----
cat > "$GITOPS_PATH/mongodb-netpol.yaml" <<'EOF'
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: mongodb-ingress
spec:
  podSelector:
    matchLabels:
      component: mongodb-nationalparks
  policyTypes:
    - Ingress
  ingress:
    - from:
        - podSelector:
            matchLabels:
              component: nationalparks
      ports:
        - protocol: TCP
          port: 27017
EOF
----
+
This policy selects only pods labeled `component=mongodb-nationalparks`.
Ingress is permitted only from pods in the same namespace labeled `component=nationalparks`, on port `27017`.
All other inbound connections to the database pods are dropped.

. Add the new file to the Kustomize resource list:
+
[source,bash,role=execute]
----
python3 - "$GITOPS_PATH/kustomization.yaml" <<'PY'
import sys, pathlib, re

path = pathlib.Path(sys.argv[1])
text = path.read_text()

entry = "  - mongodb-netpol.yaml\n"
if "mongodb-netpol.yaml" in text:
    print("Already listed — no change made.")
else:
    text = re.sub(r'(^resources:\n)', r'\1' + entry, text, flags=re.MULTILINE)
    path.write_text(text)
    print("Added mongodb-netpol.yaml to kustomization.yaml")
PY

cat "$GITOPS_PATH/kustomization.yaml"
----

. Preview the rendered output before committing:
+
[source,bash,role=execute]
----
oc kustomize "$GITOPS_PATH"
----
+
Confirm that the NetworkPolicy appears with the correct `podSelector` and `ingress` rule, and that `namespace` in the rendered output matches `$LAB_NAMESPACE`.

. Stage, review, and commit:
+
[source,bash,role=execute]
----
git add "$GITOPS_PATH/mongodb-netpol.yaml" "$GITOPS_PATH/kustomization.yaml"
git diff --cached --stat
git diff --cached
----
+
Confirm the diff contains only the NetworkPolicy and the updated kustomization. No credentials, no namespace override files.
+
[source,bash,role=execute]
----
git commit -m "Restrict mongodb-nationalparks ingress to nationalparks backend"
git push origin "$GITOPS_BRANCH"
EXPECTED_REVISION=$(git rev-parse HEAD)
printf 'Expected revision: %s\n' "$EXPECTED_REVISION"
export EXPECTED_REVISION
----

. In the Argo CD browser UI: open your Application, select *Refresh*, inspect the diff, then select *Sync*.
If automated sync is enabled, the policy may apply before you select *Sync*. Verify the same revision.

. Confirm synchronization from the terminal:
+
[source,bash,role=execute]
----
oc get applications.argoproj.io "$ARGOCD_APP" \
  -n "$ARGOCD_NAMESPACE" \
  -o jsonpath='revision={.status.sync.revision}{"\n"}sync={.status.sync.status}{"\n"}health={.status.health.status}{"\n"}'
----
+
*Expected:* `revision` matches `$EXPECTED_REVISION`, `sync=Synced`, `health=Healthy`.

. Inspect the installed policy:
+
[source,bash,role=execute]
----
oc get networkpolicy mongodb-ingress -n "$LAB_NAMESPACE" -o yaml
----

. Verify the application is still healthy after the policy is enforced:
+
[source,bash,role=execute]
----
oc rollout status deployment/nationalparks \
  -n "$LAB_NAMESPACE" --timeout=120s

curl --fail --silent --show-error --connect-timeout 5 --max-time 15 \
  -o /dev/null -w 'Frontend status: %{http_code}\n' "$PARKSMAP_URL/"

curl --fail --silent --show-error --connect-timeout 5 --max-time 15 \
  -w 'Data records after policy: ' "$NATIONALPARKS_URL/ws/data/all" \
  | python3 -c 'import json,sys; d=json.load(sys.stdin); print(len(d))'
----
+
*Expected:* HTTP `200` and the same positive record count as before. The backend pod is still labeled `component=nationalparks`, so it remains the permitted source and the database connection is unaffected.

[NOTE]
====
NetworkPolicy rules are additive. If the platform has an `AdminNetworkPolicy` that already permits or denies this traffic, your policy combines with it. Ask the instructor if the test result differs from what this exercise predicts.
====

*Checkpoint:* The NetworkPolicy is deployed through Argo CD. The application is `Synced`, `Healthy`, and still serving park data. Your Git revision matches what Argo CD reports.

== Exercise 5: Verify RBAC Isolation (4 Minutes)

The NetworkPolicy you just added controls application-layer traffic. Kubernetes RBAC controls API-layer access. These are independent boundaries. This exercise verifies both in your environment.

. Work with your assigned partner.
Enter their namespace when prompted:
+
[source,bash,role=execute]
----
read -r -p "Partner's assigned namespace: " PEER_NAMESPACE
: "${PEER_NAMESPACE:?Partner namespace is required}"
export PEER_NAMESPACE
printf 'Partner namespace: %s\n' "$PEER_NAMESPACE"
----
+
Confirm that `$PEER_NAMESPACE` differs from `$LAB_NAMESPACE`.

. Test API access to the partner's namespace using your student identity:
+
[source,bash,role=execute]
----
oc auth can-i list pods -n "$PEER_NAMESPACE"
oc get pods -n "$PEER_NAMESPACE" 2>&1 | head -3
----
+
*Expected:* `no` from the authorization check, and a `Forbidden` error from the API request. Your `RoleBinding` in `$LAB_NAMESPACE` does not extend to the partner's namespace.

. Verify that your own namespace is still readable:
+
[source,bash,role=execute]
----
oc auth can-i list pods -n "$LAB_NAMESPACE"
oc get pods -n "$LAB_NAMESPACE" -l "$APP_SELECTOR" --no-headers | wc -l
----
+
*Expected:* `yes` and a positive pod count.

. Record the evidence:
+
[cols="2,1,1",options="header"]
|===
| Check | Result | Boundary type

| List pods in own namespace
| `yes` / pod count
| RBAC (API)

| List pods in partner namespace
| `Forbidden`
| RBAC (API)

| National Parks data endpoint returns records
| positive count
| Application (HTTP)

| MongoDB blocked to non-`nationalparks` pods
| NetworkPolicy enforced
| Network (L4)
|===

. Ask your partner to confirm that their own map and data endpoint still work. The NetworkPolicy you each added is namespace-scoped; it does not affect the other participant's namespace.

*Checkpoint:* You can explain why a pod in your namespace can still reach the `nationalparks` backend via HTTP while its API resource list is denied to other identities, and why the database NetworkPolicy does not affect traffic between namespaces.

== Troubleshooting

[cols="2,3",options="header"]
|===
| Symptom | Next step

| Argo CD Application shows `OutOfSync` before your commit
| Ask the instructor to check whether drift exists from a previous session. Do not sync until the baseline state is understood.

| `git clone` or `git push` fails
| Confirm the repository URL does not embed credentials. Use the token or SSH key the instructor provided separately.

| `oc kustomize` reports a missing resource file
| Confirm the filename in `kustomization.yaml` matches the file you created exactly.

| Argo CD sync fails with a permission error
| The AppProject or Argo CD controller may not permit `networking.k8s.io/NetworkPolicy`. Ask the instructor to add it.

| Data endpoint returns empty after policy sync
| The `nationalparks` pod may not carry the expected `component=nationalparks` label. Run `oc get pods -n "$LAB_NAMESPACE" --show-labels` and compare with the NetworkPolicy `podSelector`.

| Frontend loads but map shows no markers
| The backend Route or backend-to-database connection may be affected. Check `nationalparks` pod logs and events.

| `oc auth can-i list pods -n "$PEER_NAMESPACE"` returns `yes`
| An unexpected ClusterRoleBinding may exist. Ask the instructor to check tenant permissions.

| Partner namespace check returns a different error than `Forbidden`
| Confirm the namespace name with your partner. A typo returns `NotFound`, not `Forbidden`.
|===

== Facilitator Preparation

Before delivering this module:

. Provision one application namespace per participant and verify that student accounts cannot list pods in a neighbor's namespace.
. Deploy the full National Parks stack (`parksmap`, `nationalparks`, `mongodb-nationalparks`) in each namespace and confirm the application is healthy before students arrive.
. Confirm that all three pod templates carry the `component` label (`parksmap`, `nationalparks`, `mongodb-nationalparks`) and the `app.kubernetes.io/part-of=national-parks-app` selector.
. Provide a writable Git repository and branch per participant. Configure repository authentication and confirm the participant can clone and push.
. Create an Argo CD Application per participant targeting the correct source path and the participant's namespace. Confirm the Application reports `Synced` and `Healthy` before the session.
. Add `networking.k8s.io/NetworkPolicy` to the AppProject's permitted resource kinds.
. Confirm the Argo CD controller has permission to create NetworkPolicy resources in student namespaces.
. Arrange partner pairs. Confirm both participants share a working pod-to-pod baseline only if you intend to include a network-level cross-namespace test (this module tests API isolation, not pod-to-pod networking — the NetworkPolicy exercise is scoped within the student's own namespace).
. Confirm the platform network does not already block all cross-namespace pod traffic (which would make the RBAC test meaningless as a comparison).
. Run the complete exercise with two ordinary student identities before delivering the workshop.

For a 20-minute delivery, the starter files (`kustomization.yaml` and the existing application manifests) must already be committed. Only the NetworkPolicy is added during the timed session.
