= Mission National Parks: Deploy with the OpenShift 5 Console
:navtitle: Mission National Parks
:page-toclevels: 2
:experimental:

Your project is empty. A team is waiting for the National Parks map to go live. As the platform engineer, you will deploy the frontend, build the Python API from Git, add its database, and confirm that real park data reaches the browser. Then you will use OpenShift Lightspeed to investigate what you created.

This is a *25-minute, console-first deployment mission*. The image deployment, Git import, Routes, Services and YAML editor are established OpenShift capabilities; the updated Project Felt interface and live MCP-assisted investigation are the OpenShift 5 experiences in this mission.

[IMPORTANT]
.Before you begin
====
* Sign in using the workshop credentials. Deploy into your assigned *application project*, `{lab_user}`. Do not use a similarly named `-demo` project, which can host workshop services rather than your application.
* The instructor must prepare the namespace, database Secret, safe namespace-scoped service discovery permissions, accessible image registries and a working Python builder *before class*. These are not part of the timed student exercise.
* The application should **not** already be deployed in your project. If the three National Parks workloads are present, ask for a fresh/reset student project; do not delete shared resources.
* Follow the actual labels in your OpenShift 5 console if a menu name differs from the screenshot. The remaining images are clearly labelled placeholders until genuine student screenshots are captured.
* This 25-minute target depends on rehearsed registry pulls, builder availability and database start time. If a build stalls, capture its status and ask the instructor for the prepared recovery path.
====

== Mission 0: Arrive at an empty project (2 minutes)

. Open {openshift_console_url}[your OpenShift console]. Sign in as `{lab_user}`.
. Open *Projects*, select the application project *`{lab_user}`* and explore the new console navigation and Project Felt appearance.
. Open menu:Workloads[Topology] and confirm there is no `national-parks-app` grouping yet. You are about to create it.

image::module01-s00-console.png[OpenShift 5 Projects overview - replace with the student's actual application project, width=900]

*Predict:* How many Deployments and public Routes will our three-tier application eventually need?

*Checkpoint 0:* You have selected the correct namespace and can explain the difference between the application project and the separate `-demo` project if your lab has one.

== Mission 1: Put the frontend online (4 minutes)

The fastest way to begin is with an existing container image. A running frontend does not mean the application has its data yet.

. In the console's *Quick create* (`+`) menu, choose *Container images*. If the menu layout differs, find the console's create-application-from-image action.
. Select *Image name from external registry* and enter:
+
[source,text]
----
quay.io/openshiftroadshow/parksmap:latest
----
. Set the *Application name* to `national-parks-app` and the *Name* to `parksmap`.
. Choose *Deployment* as the resource and enable *Create a route*.
. Under *Labels*, add these exact entries. Keep any console-generated labels that do not conflict:
+
[source,text]
----
app=national-parks-app
component=parksmap
role=frontend
app.kubernetes.io/part-of=national-parks-app
----
. Select *Create*. Open menu:Workloads[Topology] and watch the `parksmap` Deployment move to Ready. Follow its Route link to the new browser page.

image::module01-s05-scale-before.png[Placeholder S05 - recapture the OpenShift 5 Create from Container Image form for parksmap, width=900]

*What do you notice?* The map application can be reachable before any park data is displayed. It still needs the Python API and MongoDB. Do not troubleshoot the empty map yet.

*Checkpoint 1:* One Ready `parksmap` Deployment, a Service and a browser-accessible Route exist in **your** project.

== Mission 2: Build the Python backend from Git (6 minutes)

Now create the API that serves the map's park locations. OpenShift can build and deploy a source repository through the same console.

. Open *Quick create* (`+`) -> *Import from Git*.
. Enter the documented application repository:
+
[source,text]
----
https://github.com/openshift-roadshow/nationalparks-py.git
----
. If import strategy detection chooses *Dockerfile*, select *Edit Import Strategy* and choose the available *Python* builder image. The instructor must have validated a Python 3.12-compatible builder on this cluster.
. Set *Application* to `national-parks-app`, *Name* to `nationalparks`, and *Resource type* to *Deployment*. Select *Create a route*.
. Add the following labels:
+
[source,text]
----
app=national-parks-app
component=nationalparks
role=backend
type=parksmap-backend
app.kubernetes.io/part-of=national-parks-app
----
. Select *Create*. In Topology, open `nationalparks` -> *Resources* and inspect the build. The source build may continue while you do the next mission.

image::module01-s06-scale-after.png[Placeholder S06 - recapture Import from Git and the nationalparks build progress, width=900]

[NOTE]
====
The frontend discovers this API using a Route labelled `type=parksmap-backend`. After the Route exists, open menu:Networking[Routes] -> `nationalparks` -> *YAML* and ensure that label appears under `metadata.labels`. If it is missing, add it using the YAML editor and save. The label belongs on the *Route*, not only on the Deployment.
====

image::module01-s03-route.png[Placeholder S03 - recapture backend Route details showing the discovery label, width=900]

*Checkpoint 2:* A `nationalparks` source build has started and its Deployment, Service and Route are visible. If it fails, inspect the *Builds* view and ask your instructor to verify the builder; do not switch to a random image.

== Mission 3: Add the database from YAML (5 minutes)

Your project already contains a lab-only Secret named `nationalparks-mongodb-parameters`. It holds the example database connection variables; never paste the Secret values into the lab guide or an AI chat.

. In the console, select *Quick create* (`+`) -> *Import YAML* (sometimes labelled *YAML* or *Create from YAML*).
. Copy the following prepared **two-resource** manifest into the editor. It creates a MongoDB Deployment and an internal Service, but no public Route. The password comes from the existing Secret.

[source,yaml]
----
include::example$module01-mongodb.yaml[]
----

. Review the resources: `Deployment/mongodb-nationalparks` and `Service/mongodb-nationalparks`. Select *Create*.
. Open menu:Workloads[Deployments] -> `nationalparks` -> *YAML*. In its existing application container, add the following field under that container's properties (preserve its existing `image`, `ports` and other fields):
+
[source,yaml]
----
envFrom:
  - secretRef:
      name: nationalparks-mongodb-parameters
----
. Save the Deployment change. This starts a new backend rollout using the same database Secret as MongoDB.
. Wait until MongoDB and `nationalparks` are Ready. Confirm that MongoDB has a Service but **no external Route**.

image::module01-s04-service.png[Placeholder S04 - recapture the internal mongodb-nationalparks Service, width=900]

[WARNING]
====
The supplied database manifest uses the MongoDB image from Red Hat's National Parks tutorial and *temporary* storage for a disposable workshop. The instructor must verify that the selected image can be pulled, runs under the cluster's security settings and accepts the Secret's variables. This is not a production database configuration.
====

*Checkpoint 3:* Your project has three workload components and the database remains internal. If the backend build or database pull is still progressing, show the instructor rather than claiming this checkpoint passed.

== Mission 4: Bring National Parks to life (3 minutes)

. Open menu:Networking[Routes] -> `nationalparks`, and copy its URL.
. **Once**, for your disposable workshop database only, open the backend URL with `/ws/data/load` appended. This endpoint *changes* the database, so never use it as a recurring health check.
. Open the backend `/ws/data/all` endpoint and verify that it returns a non-empty array of parks. A response from `/ws/healthz/` alone does not prove the database works.
. Open the `parksmap` Route again and refresh the map. You should now see park markers; select one.
. Return to *Topology* and identify `parksmap`, `nationalparks` and `mongodb-nationalparks` in the `national-parks-app` group.

image::module01-s02-topology.png[Placeholder S02 - recapture the three healthy workloads in OpenShift 5 Topology, width=900]

*Checkpoint 4:* Two application Routes work, the dataset is non-empty and the map shows park markers. The MongoDB Service has no external Route.

== Mission 5: Verify the live application using OpenShift 5 MCP (4 minutes)

The *MCP server for Red Hat OpenShift* is a key OpenShift 5 feature. Your instructor has configured the Lightspeed read path separately; use it to check real resources, not to run deployment or scaling commands.

. Open *OpenShift Lightspeed* from the console chat icon.
. Send this read-only prompt, scoped to your application namespace:
+
[source,text,subs="attributes+"]
----
Use the live OpenShift MCP read tools only in namespace {lab_user}.
Inspect Deployments parksmap, nationalparks and mongodb-nationalparks;
Services parksmap, nationalparks and mongodb-nationalparks;
and Routes parksmap and nationalparks.

Report ready replica counts, which Services have public Routes,
and the actual Route hostnames. Show the successful tool calls
and their resource evidence. If live tools are unavailable,
say so explicitly. Do not inspect Secrets or change resources.
----
. Verify at least one Deployment and Route yourself in *Topology* and menu:Networking[Routes].

image::module01-s07-lightspeed.png[Placeholder S07 - recapture real Lightspeed MCP tool evidence matching the OpenShift console, width=900]

*Checkpoint 5:* Mark one honest result: *verified MCP live read*, *AI interpreted supplied text only*, or *live MCP unavailable*. A fluent response without a successful tool result is not evidence.

The image/Git/YAML deployment process, Builds, Topology, Routes and Services are long-standing OpenShift capabilities. Ingress defaults such as HAProxy 3.2 can be investigated separately with instructor-provided controller evidence.

== Troubleshooting quick reference

[cols="2,3",options="header"]
|===
| Symptom | Action
| Only `user-...-demo` is visible | Ask the instructor to grant access to your actual application namespace before deploying.
| Image import fails | Verify the external registry is reachable. Use the prepared instructor recovery path; do not substitute untested images.
| Python build is not ready | Open its Build details/logs and report the actual error. It may exceed this 25-minute timebox.
| MongoDB is not Ready | Check that the instructor-provided Secret exists; report pull failures or pod events without exposing credentials.
| Map has no markers | Confirm the backend Route's `type=parksmap-backend` label, service discovery permissions and non-empty `/ws/data/all`.
| Lightspeed has no successful tool result | Use the console for verification and mark MCP access as unverified.
|===
