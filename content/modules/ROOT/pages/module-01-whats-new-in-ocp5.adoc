= Mission National Parks: Deploy with the OpenShift 5 Console
:navtitle: Mission National Parks
:page-toclevels: 2
:experimental:

The National Parks application has not been deployed to your workshop project yet. Your project may already contain Showroom, GitOps or other workshop services; leave those resources alone. As the platform engineer, you will deploy the frontend, build the Python API from Git and create your own database Secret. The supplied MongoDB Deployment has a *deliberately outdated image*: you will use OpenShift Lightspeed and its built-in Kubernetes MCP integration to diagnose the failure, then apply the verified image-only fix yourself in the OpenShift console. Finally, you will load real park data and recover the map.

This is a *50-minute, console-first deployment and recovery mission* using *OpenShift Lightspeed 2.0*. Image deployment, Git import, Secrets, Routes, Services and the YAML editor are established OpenShift capabilities; the updated Project Felt interface and Lightspeed 2.0 *Troubleshooting* mode, with reviewed live MCP read calls, are the OpenShift 5 experiences in this mission.

== Mission 5: Apply the MongoDB image fix in the console (10 minutes)

Lightspeed 2.0 has identified the most likely cause, but *the built-in MCP toolset tested for this workshop* did not expose `resources_create_or_update`, `resources_scale` or `resources_delete`. Even if your MCP server reports `read_only = false`, that setting does *not* guarantee these tools are available. Do not attempt an AI-initiated write during this lab. You will now make the smallest controlled change yourself, using the OpenShift console.

The approved recovery image is the MongoDB Community Server `8.0.32` UBI 9 image. The YAML you imported in Mission 3 already includes initialization settings for *both* image families; the *only requested Deployment modification* is the `mongodb` container's `image` field. Do not recreate your Secret, change the Service, change storage or delete the Deployment.

. Compare the three clues from Mission 4 with the proposed recovery: the Python API expects a newer MongoDB protocol, and the old MongoDB 3.2 image cannot understand it. Confirm that the **only change required by this lab** is the database container image.
. In the OpenShift console, ensure you are still in project **`{user}-demo`**. Navigate to *Workloads* -> *Deployments* -> `mongodb-nationalparks`.
. Open the *YAML* tab and choose *Edit* (or use *Actions* -> *Edit Deployment* if that is how your console presents it). Locate the container named `mongodb` under `spec.template.spec.containers`. Change **only** its `image` value:
+
[source,yaml]
----
image: quay.io/mongodb/mongodb-community-server:8.0.32-ubi9-slim
----
. Review the edited YAML before selecting *Save*. Keep all `env`, `envFrom`, Secret references, volumes, volume mounts, Services, labels and selectors exactly as they were. **Do not paste an entirely new Deployment manifest.** Saving this image-field change triggers a new rollout.
. Return to the Deployment's *Details* and *Pods* tabs. Verify that the new Pod becomes `Running` and `Ready`, and that the container image shown in *YAML* is:
+
[source,text]
----
quay.io/mongodb/mongodb-community-server:8.0.32-ubi9-slim
----
. Open the new MongoDB Pod's *Logs* tab. Check for MongoDB `8.0.x` startup and successful initialization of the application's database user. Confirm that the old `cannot translate opcode 2013` error no longer appears in new requests.
. Retry the backend `/ws/data/all` endpoint. It should respond without a driver compatibility error (an empty list is expected until data is loaded in Mission 6).

[IMPORTANT]
====
This is a *disposable lab database* using `emptyDir` storage. The image replacement starts a new database instance; this procedure would not be safe for a production MongoDB upgrade with existing data. If the new Pod fails to start or the application cannot authenticate, stop and show the instructor the Pod events and logs. Do not repeatedly change images, remove security settings or expose Secret values.

== Troubleshooting quick reference

[cols="2,3",options="header"]
|===
| Symptom | Action
| `{user}-demo` is not visible | Ask the instructor to grant access to the existing workshop project. Do not create a new project or deploy into `default`.
| *Error loading projects* on the image form | Confirm you can select `{user}-demo`; report the project-access error instead of selecting another namespace.
| Image import fails | Verify the external registry is reachable. Use the prepared instructor recovery path; do not substitute untested images.
| Python build is not ready | Open its Build details/logs and report the actual error. It may exceed this 50-minute timebox.
| `Couldn't create container` / `secret "nationalparks-mongodb-parameters" not found` | In *Workloads* -> *Secrets*, check that **you created** `nationalparks-mongodb-parameters` in `{user}-demo` with the exact spelling. If missing, create it using Mission 3. Do not remove `envFrom` or delete the Deployment; OpenShift retries after the Secret exists.
| MongoDB is not Ready | Confirm your Secret and `mongodb-nationalparks-bootstrap` ConfigMap exist in the correct project; report pull failures, UID/volume permission errors or Pod events without exposing credentials.
| `cannot translate opcode 2013` / Python `ServerSelectionTimeoutError` | *Expected in Mission 3.* MongoDB 3.2 cannot process the current PyMongo driver protocol. Proceed to the MCP troubleshooting and image-recovery missions; do not change the database Secret.
| MongoDB 8 starts but app authentication fails | Inspect MongoDB bootstrap logs for `createUser` errors and check the ConfigMap volume is mounted. Do not expose or recreate the student's Secret; ask the instructor to check its *key names* and initialization only.
| MCP reports `resources_create_or_update` unavailable | This was observed with the workshop's Lightspeed 2.0 built-in toolset. Continue with Mission 5's human-applied Deployment image change. No additional MCP server is needed.
| Lightspeed does not offer *Troubleshooting* | Ask the instructor to verify Operator 2.0, `OLSConfig` readiness, model connectivity and built-in MCP tool access. Do not install another MCP server or grant cluster-wide permissions.
| Map has no markers after recovery | Check `/ws/data/all` is non-empty, the backend Route **and Service** have `type=parksmap-backend`, and `/ws/backends/list` contains the backend. Confirm the ParksMap Pod uses `parksmap-discovery` and its Role allows Routes and Services `get/list/watch` plus backend Endpoints `get/watch`. Inspect ParksMap logs for `Forbidden` before changing anything.
| ParksMap Route says *Application is not available* | Check Pod restarts and readiness, `oc get endpoints parksmap`, and prior container logs. A crash loop can follow repeated failed Kubernetes watches; fix the precise missing permission before a controlled restart. Do not restart all project Pods.
| Lightspeed has no successful live tool result | Use the console for evidence and mark MCP access as unverified.
|===
