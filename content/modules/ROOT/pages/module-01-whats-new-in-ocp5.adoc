== Start here: Log in to OpenShift

Open the Showroom *Terminal* tab and authenticate using your assigned workshop credentials *before running any other +oc+ commands*:

[source,bash,subs="attributes+",role=execute]
----
export KUBECONFIG="$HOME/.kube/lb1858-{user}.config"
mkdir -p "$HOME/.kube" &&
oc login --server={openshift_api_url} --username={user} --password='{password}' --insecure-skip-tls-verify &&
oc whoami | grep -Fx -- '{user}'
----

Verify that +oc whoami+ returns {user}. This is a disposable lab environment: the +--password+ option can expose your password in shell history and process listings. Do not reuse this password on a personal or production cluster.


Deploy the National Parks frontend, Python API and MongoDB 8 in your existing workshop project. The MongoDB Service contains a deliberately incorrect port. Use Lightspeed 2.0.1 Troubleshooting to diagnose the failure, approve a narrowly scoped MCP repair, and verify the change before loading park data. Leave Argo CD, Gitea and other workshop workloads alone.

This is a *25–30-minute, console-first workshop* using *OpenShift Lightspeed 2.0*. The guided walkthrough targets 28 minutes, with up to 2 minutes for transitions.

These timings assume your instructor has already verified image pulls, the Python build, student permissions, Lightspeed MCP read/write tools, tool approval and Argo CD/Gitea isolation. If a prerequisite fails, troubleshoot it separately rather than counting it against the lab. Lightspeed investigates and proposes an approved Service repair; a manual console fallback is available if the AI write path fails.

== Mission 5: Approve and verify Lightspeed's MongoDB Service repair (3 minutes)

The goal is to have *Lightspeed* perform one approved MCP write, not just describe a command for you to run. A chat message saying "I request approval" is *not* a tool approval. The required approval appears as a separate tool approval request in the Lightspeed interface.

. Before requesting a change, open *Networking → Services → mongodb-nationalparks → Details* and find *Service routing*. Under *Service port mapping*, compare *Port* with *Pod port or name*.
+
image::module01-05-port-before.jpg[MongoDB Service routing before approval with Service port 27017 and target port 27018,width=900,link=self,window=_blank]
+
To read the same pair in the authenticated student terminal, run:
+
[source,bash,subs="attributes+",role=execute]
----
oc get svc mongodb-nationalparks -n {user}-demo \
  -o jsonpath='{.spec.ports[0].port}{" -> "}{.spec.ports[0].targetPort}{"\n"}'
----
+
Expected: `27017 -> 27018`. If you see `27017 -> 27017`, the fault is already fixed. If you see `27017 -> mongodb`, this named targetPort also correctly resolves to the MongoDB container's named port; *it is not a broken state*. Do not modify an already-working Service. Ask the instructor to reset the scenario.
. In the *same Lightspeed Troubleshooting conversation* as Mission 4, send the following:
+
[source,text,subs="attributes+"]
----
Your live investigation identified Service/mongodb-nationalparks with
spec.ports[0].targetPort: 27018, while Deployment/mongodb-nationalparks
defines containerPort: 27017.

Prepare an MCP write to repair ONLY Service/mongodb-nationalparks in
namespace {user}-demo. First retrieve the complete live Service manifest.
Using resources_create_or_update, change ONLY spec.ports[0].targetPort
from 27018 to the numeric value 27017, not the named value "mongodb".
Keep all existing Service metadata, labels, annotations, selectors,
cluster IP settings and other port fields unchanged.

Invoke the actual MCP tool-approval workflow and wait for my approval.
Do not treat this chat prompt as approval to execute the change.
Do not modify Secrets, Deployments, other Services or other namespaces.
After the approved write, read the Service again and verify its targetPort.
----
. When Lightspeed displays *Review required*, open *View action details*.
+
image::module01-05-review-required.jpg[Review required on the Lightspeed tool approval card,width=720,link=self,window=_blank]
+
Compare the proposed `resources_create_or_update` manifest with the live YAML for *Service/mongodb-nationalparks* in *{user}-demo*. The only change should be the numeric `spec.ports[0].targetPort` from `27018` to `27017`. Check that `type: ClusterIP` stays under `spec` and that the cluster IP, selector and other port fields match. *Approve* that one-field change. *Reject* a proposal that moves `type` to the top level or changes anything else.
+
image::module01-05-action-details.jpg[Lightspeed action details with proposed targetPort 27017 and the Reject and Approve controls,width=860,link=self,window=_blank]

== Troubleshooting quick reference

[cols="2,3",options="header"]
|===
| Symptom | Check
| Cannot see `{user}-demo` | Sign in as your own student account.
| Python build fails | Open *Builds* -> *Logs* and inspect the error.
| MongoDB Pod not Ready | Check the Secret name, bootstrap ConfigMap and Pod events.
| Backend cannot retrieve data in Mission 3 | Expected. Investigate with Lightspeed before fixing the MongoDB Service.
| Lightspeed cannot inspect resources | Verify namespace and read permissions; notify the instructor if the safety classifier rejects a normal tool response.
| Lightspeed describes approval but never invokes MCP | Ask it to invoke `resources_create_or_update` and use the actual tool approval interface; use the manual fallback if unavailable.
| Backend still cannot connect after Mission 5 | Confirm the MongoDB Service `port` and numeric `targetPort` are both `27017`, and inspect backend logs.
| API returns records but map is blank | Follow the discovery and frontend restart checks in Mission 6.
|===
