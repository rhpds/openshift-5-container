= What's New in OCP 5
:navtitle: What's New in OCP 5
:page-toclevels: 2

Your first task as a platform engineer is to establish what your cluster can actually do. In this module, you will inspect your environment, create a small test resource, and check whether OpenShift Lightspeed can retrieve live information about it. You will compare the AI response with the Kubernetes API before relying on it.

[cols="1,3",options="header"]
|===
| Duration | Format
| 20 minutes | Guided hands-on exercises in your assigned namespace
| Optional: 10–15 minutes | Choose one feature tour with your instructor
|===

[IMPORTANT]
====
This guide uses the https://rhpds.github.io/ocp5-ea-showroom/modules/index.html[OpenShift 5 Early Access reference]. Its feature descriptions are evaluation material, not a complete OpenShift 5 release specification. Availability, APIs, UI labels and support status depend on the installed build and configuration.

The configured workshop target is *{ocp_version}*. Verify the running version below. The early-access reference uses a cluster-admin environment; this workshop uses student accounts on a shared cluster. Follow the namespace-scoped exercises on this page.
====

== Learning Objectives

* Identify your account, namespace, running cluster version and available APIs.
* Distinguish early-access features, separately installed products and capabilities carried forward from OpenShift 4.
* Verify a live Lightspeed/MCP response against a resource you created.
* Record which capabilities are available before starting application onboarding.

== Before You Begin

Your instructor provides:

* The workshop console URL and your own login credentials.
* Your assigned, pre-created namespace on the shared cluster.
* A Bash terminal with a compatible `oc` CLI.
* Confirmation of which optional early-access features are enabled for students.

Use the same terminal throughout the module so that the shell variables remain available. You will create one ConfigMap containing synthetic, non-sensitive data. The application deployment starts in Module 2.

NOTE: If the URL shown below still contains `%GUID%` or `example.com`, use the console URL supplied with your workshop credentials.

== Exercise 1: Verify Your Access (4 Minutes)

. Open {openshift_console_url}[the OpenShift console] and sign in with your student account. Select your assigned project.
. In the terminal, check your identity and API endpoint:
+
[source,bash,role=execute]
----
oc whoami
oc whoami --show-server
----
+
If the terminal is not authenticated, use your user menu in the console to obtain *Copy login command*, then run that command privately in your terminal. Do not paste your token into Lightspeed or your workshop notes. If the terminal is logged in as an administrator, switch to the supplied student account before continuing.
. Detect and set your assigned namespace:
+
[source,bash,role=execute]
----
LAB_NAMESPACE=$(oc project -q 2>/dev/null)
[ -z "$LAB_NAMESPACE" ] && LAB_NAMESPACE=$(oc whoami 2>/dev/null)
export LAB_NAMESPACE
echo "Namespace: ${LAB_NAMESPACE:?Could not detect — ensure you are logged in with your student account}"
----
+
*Expected:* your assigned namespace is printed. If the value looks wrong (for example, an admin namespace), run `oc project <your-namespace>` with the value your instructor provided and re-run the block.
. Check the permissions required for this module:
+
[source,bash,role=execute]
----
oc auth can-i list pods -n "${LAB_NAMESPACE:?Set LAB_NAMESPACE}"
oc auth can-i list events -n "$LAB_NAMESPACE"
oc auth can-i get configmaps -n "$LAB_NAMESPACE"
oc auth can-i create configmaps -n "$LAB_NAMESPACE"
oc auth can-i delete configmaps -n "$LAB_NAMESPACE"
----
+
*Expected:* five `yes` responses. A `no` identifies an access prerequisite for the instructor to resolve; it does not mean the feature is absent. These checks cover your CLI identity, not the identity used by an AI service.
. Inspect your namespace:
+
[source,bash,role=execute]
----
oc get pods -n "${LAB_NAMESPACE:?Set LAB_NAMESPACE}"
oc get events -n "$LAB_NAMESPACE" --sort-by=.metadata.creationTimestamp
----
+
*Expected:* an empty namespace or only workshop bootstrap resources. `No resources found` is valid before application onboarding. It is different from `Forbidden`, which means the API rejected the request.

*Checkpoint:* You can identify your account, cluster endpoint and assigned namespace, and read resources there.

== Exercise 2: Discover the Running Platform (4 Minutes)

. Check your CLI/server versions and whether your account can read the cluster release:
+
[source,bash,role=execute]
----
oc version
if [ "$(oc auth can-i get clusterversions.config.openshift.io/version)" = yes ]; then
  oc get clusterversion.config.openshift.io version \
    -o jsonpath='{.status.desired.version}{"\n"}{range .status.conditions[*]}{.type}{"="}{.status}{"\n"}{end}'
else
  printf '%s\n' 'Ask the instructor to show the cluster release and update status.'
fi
----
+
Record the reported release and whether an update is progressing. `status.desired.version` is the target release; during an update it does not prove every component has reached that version. The instructor can confirm the completed release from the cluster update history. A Kubernetes server version is also not an OpenShift release number.
. Discover the APIs advertised by the server:
+
[source,bash,role=execute]
----
oc api-resources --verbs=list -o wide
----
+
Look through the output for the following kinds. Record the API group/version shown by your cluster rather than guessing one from an example manifest.
+
[cols="1,3",options="header"]
|===
| Kind | What it helps you discover
| `OLSConfig` | Lightspeed configuration API
| `AgenticRun` | Agentic investigation API
| `PersesDashboard` | Perses dashboard API
| `MCPServerRegistration` | MCP federation registration API
| `Central` / `SecuredCluster` | ACS configuration APIs
| `ClusterExtension` | OLM v1 extension API
|===
+
An advertised API proves that the server exposes that resource type. It does *not* prove that an instance exists, its controller is healthy, the feature is enabled, or your account can use it. A missing type means it was not found in this discovery result; have the instructor check installation and discovery errors before concluding why.
. In the console, check whether you can see the Lightspeed chat entry point. The early-access reference shows a chat icon at the bottom right. Note whether a *troubleshooting* mode is offered. Also note whether *Observe > Metrics* and *Observe > Dashboards (Perses)* are visible to your account.

*Checkpoint:* You have recorded the actual release evidence and which feature entry points are visible. You have not treated the configured workshop version as proof of feature availability.

== Exercise 3: Create a Resource to Verify (4 Minutes)

You will create a ConfigMap with a fresh marker. The marker gives you a value that Lightspeed must retrieve from the cluster to answer the next exercise correctly.

. Check whether the exercise name is already in use:
+
[source,bash,role=execute]
----
oc get configmap module01-discovery -n "${LAB_NAMESPACE:?Set LAB_NAMESPACE}" \
  --ignore-not-found -o name
----
+
*Expected:* no output and no error. If the object exists, stop and ask the instructor to confirm its ownership or reset this exercise. Do not overwrite or delete an existing resource.
. Create the ConfigMap. This uses `create`, so it will fail rather than overwrite a resource with the same name:
+
[source,bash,role=execute]
----
MODULE01_MARKER="observation-$(date -u +%Y%m%dT%H%M%SZ)-${RANDOM}"
MODULE01_UID=$(oc create configmap module01-discovery \
  -n "${LAB_NAMESPACE:?Set LAB_NAMESPACE}" \
  --from-literal=purpose=module-01-live-data-check \
  --from-literal=observation="$MODULE01_MARKER" \
  -o jsonpath='{.metadata.uid}')
printf 'Created resource UID: %s\n' "$MODULE01_UID"
----
+
*Expected:* a non-empty UID and no error. If creation fails, resolve the error before continuing. Keep this terminal open: the UID will identify your resource during cleanup.
. Read selected fields from the API:
+
[source,bash,role=execute]
----
oc get configmap module01-discovery -n "${LAB_NAMESPACE:?Set LAB_NAMESPACE}" \
  -o jsonpath='{.metadata.name}{"\n"}{.metadata.namespace}{"\n"}{.data.observation}{"\n"}{.metadata.resourceVersion}{"\n"}'
----
+
*Expected:* the resource name, your namespace, the fresh marker and its resource version. Keep these results for comparison, but do not give the marker or resource version to Lightspeed yet.

*Checkpoint:* You have created and read one resource in your namespace. No application pods or cluster-wide resources were created.

== Exercise 4: Verify a Lightspeed Answer (6 Minutes)

=== If Live MCP Access Is Configured

. Open Lightspeed. Select *troubleshooting* mode if your build offers it and your instructor has enabled it for this exercise.
. Copy the following prompt, replace `YOUR_ASSIGNED_NAMESPACE` with your actual namespace, and send it. Do not include the marker or the previous command output:
+
[source,text,role=copypaste]
----
Read only the ConfigMap module01-discovery in namespace YOUR_ASSIGNED_NAMESPACE.
Return its data.observation value and metadata.resourceVersion.
Identify the read tool you used and the resource it queried.
Do not change resources, run commands in pods, or read Secrets.
If you cannot access live cluster data, say so; do not infer the values.
----
+
If a tool approval appears, inspect its action and namespace. Proceed only with the intended read request. Decline requests to execute commands in pods or change resources.
. Compare the answer with a fresh API read:
+
[source,bash,role=execute]
----
oc get configmap module01-discovery -n "${LAB_NAMESPACE:?Set LAB_NAMESPACE}" \
  -o jsonpath='{.data.observation}{"\n"}{.metadata.resourceVersion}{"\n"}'
----
+
*Expected:* the marker and resource version match, and the available tool details identify the same resource and namespace. If the resource changed between reads, inspect the difference and repeat the read before judging the result. Do not accept a generic explanation of ConfigMaps as proof of live access.
. Ask a follow-up question:
+
[source,text,role=copypaste]
----
Explain why matching a fresh observation value is stronger evidence of live
cluster access than a general description of this ConfigMap. What limitations
remain in this check?
----

This verifies one successful read. It does not prove access to metrics, logs or traces, nor does it prove that other namespaces are isolated from the AI service. Those require separate checks.

NOTE: A read-only prompt is an instruction, not a security boundary. The platform must enforce permissions and tool restrictions. Your instructor must verify the identity and access model used by the configured MCP integration.

=== If Live MCP Access Is Unavailable

If Lightspeed has no live tools, reports an access error, or is not installed, record *live access not verified*. You can still complete the CLI exercises.

If chat is available, paste only the synthetic fields printed in Exercise 3 and ask Lightspeed to explain them. Label this result *analysis of supplied data*. A correct answer in this mode does not demonstrate live cluster access. If chat is unavailable, discuss the same distinction with your instructor.

*Checkpoint:* Classify your outcome as *verified live read*, *analysis of supplied data*, or *unavailable*. Record a mismatch as a failed check to investigate, rather than a successful live read.

== Exercise 5: Record Findings and Clean Up (2 Minutes)

. Add these observations to your workshop notes:
+
[cols="2,3",options="header"]
|===
| Observation | Record
| Account and namespace | Your assigned identity and project
| Cluster release | Reported version, update status and source of confirmation
| Lightspeed/MCP result | Verified live read, supplied-data analysis, unavailable, or failed check
| Feature access | Entry points/APIs observed and anything requiring instructor confirmation
| Follow-up | One question to resolve before the incident investigation module
|===
. Delete only the ConfigMap created in Exercise 3. This checks that the current object still has the UID returned by your successful creation:
+
[source,bash,role=execute]
----
if [ -n "${MODULE01_UID:-}" ]; then
  CURRENT_UID=$(oc get configmap module01-discovery \
    -n "${LAB_NAMESPACE:?Set LAB_NAMESPACE}" --ignore-not-found \
    -o jsonpath='{.metadata.uid}')
  if [ "$CURRENT_UID" = "$MODULE01_UID" ]; then
    oc delete configmap module01-discovery -n "$LAB_NAMESPACE"
  else
    printf '%s\n' 'Object is absent or its UID differs; nothing was deleted.'
  fi
else
  printf '%s\n' 'No creation UID in this terminal; ask the instructor before cleanup.'
fi
----
. Confirm the resource is gone:
+
[source,bash,role=execute]
----
oc get configmap module01-discovery -n "${LAB_NAMESPACE:?Set LAB_NAMESPACE}" \
  --ignore-not-found -o name
----
+
*Expected:* no output and no error. Keep your namespace and terminal session for application onboarding.

== Optional Feature Tour (Choose One, 10–15 Minutes)

Choose a tour your instructor has enabled. The shared workshop might not contain every component from the early-access environment.

=== Tour A: Metrics and Inline Perses Charts

. Open *Observe > Metrics* and select your assigned project if the view provides a project selector.
. Replace `YOUR_ASSIGNED_NAMESPACE` in this query with your namespace and run it:
+
[source,promql,role=copypaste]
----
sum by (pod) (
  rate(container_cpu_usage_seconds_total{
    namespace="YOUR_ASSIGNED_NAMESPACE",
    container!="",container!="POD",pod!=""
  }[5m])
)
----
. Record whether the query returns data, an empty result or an access error. CPU usage here is measured in CPU cores. An empty result can be expected before your application exists; it does not mean CPU usage is zero.
. If the Lightspeed metrics and chart integration is enabled, ask it to graph this exact query over the last 15 minutes. Compare the namespace, query and time range with the console result. If there is no data, record that outcome instead of asking it to invent a chart.

*Checkpoint:* Explain the difference between a successful empty query, a denied query and a chart backed by actual samples. Dashboard creation and export can follow in a later observability exercise.

=== Tour B: Review an Existing Agentic Investigation

. Ask the instructor to identify a pre-existing run that your account may view. If student access is unavailable, follow the instructor's console demonstration.
. Open the *Agentic Runs* view supplied by the installed plugin and select that run. Record its trigger, current state, affected namespace and the evidence behind its proposed action.
. Identify which stages require approval in this environment. Review the proposal without approving execution, rerunning the investigation or changing its policy.

*Checkpoint:* Distinguish gathering evidence, proposing a change and authorising execution. A proposed fix still needs verification against the application and its GitOps source.

=== Tour C: Inspect MCP Gateway or ACS

. Choose one service your instructor has made available to your account.
. For *Connectivity Link*, open *Overview* or *Policy Topology*, scoped to the instructor-assigned gateway resources. Identify a backend registration, its route, an authentication/authorisation policy and a rate-limit policy. Record which relationship each policy controls; a diagram alone does not prove enforcement.
. For *ACS*, use the supplied Central URL and permitted scope. Inspect an existing workload's vulnerability results or file activity findings. Record the workload, finding type and scan/observation time. Ask the instructor to show the relevant feature configuration if results are absent.

*Checkpoint:* Explain why gateway tool access policies and ACS security findings require additional components beyond the OpenShift core installation.

=== Instructor Demonstration: Update Assessment

If the appropriate preview is installed, the instructor can show the cluster update page and an existing AI assessment. Compare its recommendation with the stated evidence, including degraded Operators, alerts and update conditions. Distinguish an agentic analysis record from a user-initiated Lightspeed chat assessment.

Review only: do not start an update, deliberately degrade an Operator, change approval policies or disable GitOps reconciliation on this shared cluster. If there is no offered update or no assessment, record that limitation.

== Troubleshooting

[cols="2,3",options="header"]
|===
| Symptom | Next step
| `oc` is missing or login fails | Use the provided workshop terminal or obtain the matching CLI and login command from the console. Ask the instructor if authentication still fails.
| Wrong or unset namespace | Repeat the namespace selection in Exercise 1 in the same terminal.
| `Forbidden` | Confirm your identity and the specific `oc auth can-i` check. Ask the instructor to correct the scoped permissions.
| `No resources found` | Confirm the namespace and resource type. An empty result can be valid before Module 2.
| `AlreadyExists` for the ConfigMap | Stop; do not overwrite it. Have the instructor establish ownership before a reset.
| Lightspeed is visible but cannot retrieve the marker | Check the configured MCP connection and effective identity with the instructor. Use the supplied-data fallback and record live access as unverified.
| Missing troubleshooting mode, Agentic Runs or Perses view | Record the feature as unavailable to your account in this build and continue with the core exercises.
| Metrics query returns no series | Check namespace, time range, monitoring configuration and whether workloads are running. Do not interpret absent data as zero usage.
|===

== Completion Check

You are ready to move on when you can:

* Show your account, namespace and cluster release evidence.
* Explain why an API or menu entry does not prove a configured, working feature.
* Show your ConfigMap read/cleanup results and classify the Lightspeed outcome honestly.
* Identify at least two early-access capabilities and the components they depend on.
* Explain how you will verify an AI recommendation before changing an application.

== Instructor Preparation and Reference Notes

Before delivering this module, rehearse it using an actual student identity on the target build:

* Provision the assigned namespaces and the permissions checked in Exercise 1. Leave `module01-discovery` unused and outside any GitOps-managed application inventory.
* Verify console/CLI login and provide the actual console URL. Confirm the cluster release and update status for students who cannot read `ClusterVersion`.
* For the live-read path, configure Lightspeed/model access and the OpenShift MCP integration; verify effective credentials and namespace access. Use least privilege and server-side read-only tool controls where available. Do not grant students cluster-admin access to make this exercise work.
* Confirm that the marker read works through the selected tool and that the student can inspect enough tool evidence to verify it. Confirm the fallback path for environments without this integration.
* Announce which optional tours are available. Keep shared agentic triggers, remediation execution, update operations and platform configuration under instructor control.

The source https://rhpds.github.io/ocp5-ea-showroom/modules/cluster-details.html[technical cluster details] describe a separately provisioned evaluation environment, including components that this workshop's bootstrap may not yet install. Treat the checks above as delivery prerequisites; this page does not certify a live environment.
