= Mission National Parks: Deploy with the OpenShift 5 Console
:navtitle: Mission National Parks
:page-toclevels: 2
:experimental:

Deploy the National Parks frontend, Python API and MongoDB 8 in your existing workshop project. The MongoDB Service contains a deliberately incorrect port. Use Lightspeed to diagnose the connection failure, repair the Service and load park data. Leave Argo CD, Gitea and other workshop workloads alone.

This is a *50-minute, console-first workshop* using *OpenShift Lightspeed 2.0*. Lightspeed investigates; you apply the repair.

[cols="1,1,1,1,1,1,1,1",options="header"]
|===
| 0–2 | 2–11 | 11–17 | 17–27 | 27–33 | 33–43 | 43–48 | 48–50 min
| Select project | Frontend + discovery permissions | Python API | MongoDB 8 + wrong port | Diagnose with Lightspeed | Repair MongoDB Service | Load data + map | Sign-off
|===

. Verify the RoleBinding namespace is `{user}-demo`, then select *Create*. This creates a dedicated ServiceAccount, Role and RoleBinding. If creation is forbidden, ask your instructor to provision them. **Do not give `view` to the `default` ServiceAccount.**
. In the *Showroom Terminal*, check that `oc whoami` returns `{user}` (not a Showroom ServiceAccount). Then run this **single patch**:
+
[source,bash,subs="attributes+"]
----
oc patch deployment parksmap -n {user}-demo --type=merge \
  -p '{"spec":{"template":{"spec":{"serviceAccountName":"parksmap-discovery"}}}}'
oc rollout status deployment/parksmap -n {user}-demo
----
+
Expected: `deployment.apps/parksmap patched`, followed by a successful rollout. A successful rollout **alone** does not mean a failed patch succeeded.

+
[source,bash,subs="attributes+"]
----
oc get deployment parksmap -n {user}-demo \
  -o jsonpath='{.spec.template.spec.serviceAccountName}{"\n"}'
----
+
Expected:
+
[source,text]
----
parksmap-discovery
----
+
If the output is blank or says `default`, the Deployment is **not fixed**. Check that `oc whoami` returns `{user}`, then repeat the patch. A RoleBinding alone does not make the Pod use this identity. **Do not continue until this check passes.**

== Mission 3: Deploy MongoDB and observe the failure (10 minutes)

Deploy MongoDB 8. The database Pod will start, but the Python backend cannot reach it because the MongoDB Service contains a deliberate fault.

. In project \`{user}-demo\`, open *Workloads* -> *Secrets* -> *Create* -> *Key/value secret*. Name it \`nationalparks-mongodb-parameters\`. Add these five keys:

[cols="2,3",options="header"]
|===
| Key | Value
| \`DATABASE_SERVICE_NAME\` | \`mongodb-nationalparks\`
| \`MONGODB_USER\` | \`mongodb\`
| \`MONGODB_DATABASE\` | \`mongodb\`
| \`MONGODB_PASSWORD\` | Your own strong password (at least 16 characters)
| \`MONGODB_ADMIN_PASSWORD\` | A *different* strong password (at least 16 characters)
|===

+
image::module01-s09a-secret-create-menu.png[Create a key/value Secret, width=800]
+
[IMPORTANT]
====
Never copy passwords from screenshots or paste them into Lightspeed.
====

. Select *Create*. Choose *Quick create* (\`+\`) -> *Import YAML*. Import these three resources: a bootstrap ConfigMap, MongoDB Deployment and MongoDB Service.
+
[source,yaml]
----
include::example$module01-mongodb.yaml[]
----
. Open your Python backend Deployment (typically \`nationalparks\`) under *Workloads* -> *Deployments* -> *YAML* -> *Edit*. Add this to the application container, beside \`image\` and \`ports\`:
+
[source,yaml]
----

  - secretRef:
      name: nationalparks-mongodb-parameters

*Checkpoint 3:* Both workloads are Running, but the backend cannot retrieve data. **Do not load park data or change any ports yet.**

== Mission 4: Investigate with Lightspeed (6 minutes)

. Open *OpenShift Lightspeed* -> *Troubleshooting*.
+
image::module01-s09k-lightspeed-mode.png[Select Lightspeed Troubleshooting, width=850]
. Paste this prompt:
+
[source,text,subs="attributes+"]
----
My National Parks application cannot retrieve park data.

Use live Kubernetes tools to inspect Pods, Deployments, Services,
EndpointSlices and application logs in namespace {user}-demo.
Find the cause and explain how to fix it.

Do not read Secrets or change anything.
----
. Review the response. If asked, approve *only* read operations in your namespace.

[TIP]
====
*AI check:* Compare the MongoDB Service with the MongoDB Pod. The Service exposes \`27017\`, but its \`targetPort\` is \`27018\`. MongoDB listens on \`27017\`. The Pod can be Ready even though the Service forwards to the wrong port. Verify the evidence yourself; do not change Secrets or images.
====

*Checkpoint 4:* You can explain why the healthy MongoDB Pod is unreachable through its Service.

== Mission 5: Repair the MongoDB Service (5 minutes)

. Go to *Networking* -> *Services* -> \`mongodb-nationalparks\` -> *YAML* -> *Edit*.
. Find \`spec.ports\` and change **only** \`targetPort\` to \`27017\`:
+
[source,yaml]
----
ports:
  - name: mongodb
    port: 27017
    targetPort: 27017
    protocol: TCP
----
+
Keep the selector and every other field unchanged. Select *Save*.
. Verify the port in the Showroom terminal:
+
[source,bash,subs="attributes+"]
----
oc get svc mongodb-nationalparks -n {user}-demo \
  -o jsonpath='{.spec.ports[0].port}{" -> "}{.spec.ports[0].targetPort}{"\n"}'
----
+
Expected: \`27017 -> 27017\`. No MongoDB Pod restart is required.
. Open https://national-parks-app-{user}-demo.{openshift_cluster_ingress_domain}/ws/data/load[Load National Parks data,window=_blank] **once** to populate the disposable database. Then open https://national-parks-app-{user}-demo.{openshift_cluster_ingress_domain}/ws/data/all[View National Parks data,window=_blank] and confirm park records appear.

*Checkpoint 5:* The API can now read MongoDB data. You repaired one Service field without changing the image, credentials or Pod labels.

== Troubleshooting quick reference

[cols="2,3",options="header"]
|===
| Symptom | Check
| Cannot see \`{user}-demo\` | Sign in as your own student account.
| Python build fails | Open *Builds* -> *Logs* and inspect the error.
| MongoDB Pod not Ready | Check the Secret name, bootstrap ConfigMap and Pod events.
| Backend cannot retrieve data in Mission 3 | Expected. Investigate with Lightspeed before fixing the MongoDB Service.
| Lightspeed cannot inspect resources | Verify namespace and read permissions.
| Backend still cannot connect after Mission 5 | Confirm the MongoDB Service \`port\` and \`targetPort\` are both \`27017\`, and inspect backend logs.
| API returns records but map is blank | Check the \`parksmap-discovery\` ServiceAccount and \`type=parksmap-backend\` labels on backend Service and Route.
|===
