You are the platform engineer responsible for *National Parks*, a web application that displays park locations on a map. Your first task is to establish a healthy baseline on OpenShift 5, understand how requests reach the application, and verify what an AI-assisted investigation can actually observe.

You will work with the `national-parks-app` example described in the supplied OpenShift 5 Tutorials guide. Your instructor provisions a working copy in your assigned namespace before this module.

|===
| Time | Activity
| 3 minutes | Verify your identity, namespace, and running platform.
| 4 minutes | Open National Parks and check its application and data responses.
| 5 minutes | Follow a Route through its Service and EndpointSlices to the application pods.
| 5 minutes | Verify an AI-assisted ingress investigation, or complete the CLI evidence path.

| Optional: 5–10 minutes | Explore an ingress behaviour change or an installed extension with your instructor.
|===

== What You Will Learn

* Connect documented OpenShift 5 changes to a real application.
* Identify the frontend, backend, database, and their Kubernetes resources.
* Distinguish pod readiness, HTTP availability, and a working database-backed request.
* Compare an AI response with current Route and EndpointSlice evidence.
* Record workload observations that later resource-control and incident exercises can use.

== OpenShift 5 Changes to Look For

The following changes come from the supplied *OpenShift Container Platform 5.0* documentation snapshot. Check the installed build and feature configuration before expecting the same behaviour on your cluster.

[cols="2,3,3",options="header"]
|===
| Area | What the supplied documentation says | Connection to National Parks

| Platform foundation
| The release notes identify Kubernetes 1.35 and the CRI-O runtime.
| Record your actual server and OpenShift versions. A configured workshop target is not evidence of the running release.

| AI-assisted ingress and DNS investigation
| The `netedge` toolset adds ingress and DNS diagnostics to the OpenShift MCP server. It must be enabled explicitly. The release status table lists the MCP server as *Technology Preview*.
| Inspect the `parksmap` Route and its Service endpoints, then verify the findings yourself.

| Ingress behaviour
| The release notes describe HAProxy 3.2.22 as the default, with HAProxy 2.8.27 available for migration and a selectable `spec.haproxyVersion`. Request validation and some HTTP error responses change.
| Establish that the application's normal requests work. An optional exercise checks one documented request-validation behaviour.

| Image access
| Project-scoped image pull secrets for mirrored registries move to general availability in the supplied status table.
| The instructor can scope access to mirrored application images to a tenant project when that registry configuration is used.

| Update assessment
| The release notes describe AI-powered update risk and status assessments in the console.
| An instructor can explain how an application baseline supports update planning. Starting a cluster update is outside this module.
|===

== Meet the Application

[cols="1,2,2",options="header"]
|===
| Component | Resources used in this workshop | What you will verify
| Frontend | Deployment, Service, and Route named `parksmap` | The map application opens through its external URL.
| Backend | Deployment, Service, and Route named `nationalparks` | The Python service returns park records from the database.
| Database | Deployment and Service named `mongodb-nationalparks` | The backend can read the instructor-loaded dataset.
| Application grouping | `app.kubernetes.io/part-of=national-parks-app` on the application workloads and pods | The three components can be identified together without including unrelated namespace services.
|===

`national-parks-app` is the application grouping label, not a fourth Deployment. The frontend discovers backend routes; the `nationalparks` Route must have `type=parksmap-backend`. The database stays internal to the namespace.

== Exercise 1: Verify Your Environment (3 Minutes)

. Open {openshift_console_url}[the OpenShift console] and select your assigned project. If this URL still contains `%GUID%` or `example.com`, use the URL supplied with your credentials.
. Confirm your terminal identity and API endpoint:
+
[source,bash,role=execute]
----
oc whoami
oc whoami --show-server
----
+
Use your assigned student or Showroom identity. Keep login tokens out of prompts and workshop notes.
. Set the application namespace. Enter the namespace supplied by the instructor, which can differ from your login name or the namespace hosting your terminal:
+
[source,bash,role=execute]
----
read -r -p "Your assigned application namespace: " LAB_NAMESPACE
: "${LAB_NAMESPACE:?An assigned namespace is required}"
export LAB_NAMESPACE
APP_SELECTOR='app.kubernetes.io/part-of=national-parks-app'
export APP_SELECTOR
printf 'Application namespace: %s\n' "$LAB_NAMESPACE"
----
. Check the running versions:
+
[source,bash,role=execute]
----
oc version
if [ "$(oc auth can-i get clusterversions.config.openshift.io/version)" = yes ]; then
  oc get clusterversion.config.openshift.io version \
    -o jsonpath='target={.status.desired.version}{"\n"}progressing={.status.conditions[?(@.type=="Progressing")].status}{"\n"}{range .status.history[?(@.state=="Completed")]}completed={.version}{"\n"}{end}'
else
  printf '%s\n' 'Ask the instructor to show the latest completed OpenShift release.'
fi
----
+
Record the latest completed OpenShift release and any update in progress. A target version can differ from the completed release during an update. `oc version` also reports Kubernetes information; that number is not the OpenShift release number.
. Confirm that the expected Deployments exist:
+
[source,bash,role=execute]
----
oc get deployments parksmap nationalparks mongodb-nationalparks \
  -n "$LAB_NAMESPACE"
oc get pods -n "$LAB_NAMESPACE" -l "$APP_SELECTOR" -o wide
----
+
*Expected:* the three application Deployments have their desired replicas available and their application pods are Ready. Completed build pods, if present, are not serving replicas. A missing Deployment or an access error is a setup issue to resolve before the timed exercises.

*Checkpoint:* You can identify your namespace and the running release, and locate all three application components.

== Exercise 2: Establish a Working Application (4 Minutes)

=== Open the map

. In the console, open *Workloads > Topology* and select your project. Locate the `national-parks-app` group and click `parksmap`.
. Open the *Resources* tab and follow the Route link to the application. Pan or zoom the map and confirm that park markers appear. Select a marker and inspect its information.
. Retrieve the Route hosts from the API:
+
[source,bash,role=execute]
----
PARKSMAP_HOST=$(oc get route parksmap -n "$LAB_NAMESPACE" \
  -o jsonpath='{.spec.host}')
NATIONALPARKS_HOST=$(oc get route nationalparks -n "$LAB_NAMESPACE" \
  -o jsonpath='{.spec.host}')
: "${PARKSMAP_HOST:?parksmap Route has no host}"
: "${NATIONALPARKS_HOST:?nationalparks Route has no host}"
PARKSMAP_URL="https://${PARKSMAP_HOST}"
NATIONALPARKS_URL="https://${NATIONALPARKS_HOST}"
export PARKSMAP_URL NATIONALPARKS_URL
printf 'Frontend: %s\nBackend: %s\n' "$PARKSMAP_URL" "$NATIONALPARKS_URL"
----
+
This workshop's setup uses HTTPS Routes with certificates trusted by the terminal. If your setup differs, have the instructor confirm the correct URLs and trust configuration.
. Check the frontend response:
+
[source,bash,role=execute]
----
curl --fail --silent --show-error --connect-timeout 5 --max-time 15 \
  -o /dev/null -w 'Frontend HTTP status: %{http_code}\n' \
  "$PARKSMAP_URL/"
----
+
*Expected:* HTTP `200` and a working browser view.

=== Check the backend and the database-backed response

. Call the backend health endpoint:
+
[source,bash,role=execute]
----
curl --fail --silent --show-error --connect-timeout 5 --max-time 15 \
  "$NATIONALPARKS_URL/ws/healthz/"
----
+
*Expected:* an `OK` response. In the reviewed Python backend, this handler does not query MongoDB, so it does not establish database health.
. Read the park dataset and check that it contains records:
+
[source,bash,role=execute]
----
MODULE01_EVIDENCE=$(mktemp -d "${TMPDIR:-/tmp}/ocp5-module01.XXXXXX")
export MODULE01_EVIDENCE

if curl --fail --silent --show-error --connect-timeout 5 --max-time 15 \
    "$NATIONALPARKS_URL/ws/data/all" \
    -o "$MODULE01_EVIDENCE/parks.json"; then
  python3 - "$MODULE01_EVIDENCE/parks.json" <<'PY'
import json
import sys
with open(sys.argv[1], encoding="utf-8") as source:
    parks = json.load(source)
if not isinstance(parks, list) or not parks:
    raise SystemExit("No park records returned; ask the instructor to check initialization.")
print("Park records:", len(parks))
print("Example:", parks[0].get("name", parks[0].get("id", "unnamed")))
PY
else
  printf '%s\n' 'The data request failed. Resolve this before marking the application healthy.'
fi
----
+
*Expected:* a positive record count and an example park name. An empty list or a request failure means the database is not initialized; ask the instructor. Do not call `/ws/data/load` yourself.

*Checkpoint:* The frontend returns HTTP `200`, the backend returns `OK`, and the data endpoint returns park records. The application is healthy enough to continue.

== Exercise 3: Follow the Ingress Path (5 Minutes)

A working map means a request arrived at the `parksmap` pod. This exercise traces that path from the Route to the running pod.

. Check the `parksmap` Route configuration:
+
[source,bash,role=execute]
----
oc get route parksmap -n "$LAB_NAMESPACE" \
  -o jsonpath='host={.spec.host}{"\n"}termination={.spec.tls.termination}{"\n"}service={.spec.to.name}{"\n"}targetPort={.spec.port.targetPort}{"\n"}'
----
+
Record the Route hostname, TLS termination type, target Service, and target port. The termination type determines where the certificate is validated; `edge` means HAProxy decrypts before forwarding to the pod in plain HTTP.

. Check the Service selector and port mapping:
+
[source,bash,role=execute]
----
oc get service parksmap -n "$LAB_NAMESPACE" \
  -o jsonpath='selector={.spec.selector}{"\n"}port={.spec.ports[0].port}:{.spec.ports[0].targetPort}{"\n"}'
----
+
The selector labels must match the pod labels. The port mapping translates the Service port to the container port.

. List the EndpointSlices for the Service and check pod readiness:
+
[source,bash,role=execute]
----
oc get endpointslices.discovery.k8s.io \
  -l kubernetes.io/service-name=parksmap \
  -n "$LAB_NAMESPACE" \
  -o jsonpath='{range .items[*]}{range .endpoints[*]}ip={.addresses[0]}  ready={.conditions.ready}  node={.nodeName}{"\n"}{end}{end}'
----
+
*Expected:* at least one endpoint with `ready=true`. An empty list or all `ready=false` endpoints means no traffic reaches the pods despite a valid Route and Service.

. Confirm the pod labels match the Service selector:
+
[source,bash,role=execute]
----
oc get pods -n "$LAB_NAMESPACE" -l "$APP_SELECTOR" --show-labels -o wide
----
+
*Expected:* application pods are `Running` and `1/1` Ready. A pod without the selector labels will not receive Service traffic even if it is running.

. Check recent pod log output:
+
[source,bash,role=execute]
----
oc logs -n "$LAB_NAMESPACE" deployment/parksmap --tail=10 --timestamps=true
----

*Checkpoint:* You can name each resource in the path from the Route hostname to the pod: Route → Service → EndpointSlice → pod. At least one pod endpoint is ready.

== Exercise 4: Verify an AI-Assisted Investigation (5 Minutes)

The OpenShift MCP server's `netedge` toolset adds ingress and DNS diagnostics. This exercise uses it to inspect the `parksmap` Route and Service endpoints, then verifies the findings with `oc`. The MCP server is classified as *Technology Preview* in the {ocp5-release-notes}#ocp-release-notes-ai-apps_release-notes[release notes]; `netedge` must be enabled explicitly.

Your instructor will confirm whether the AI path is configured for this environment.

=== AI Path: Use the Configured MCP Tools

. Open the configured AI client. Copy the following prompt, replace `YOUR_NAMESPACE` with your actual namespace, and send it:
+
[source,text,role=copypaste]
----
Inspect the Route named parksmap in namespace YOUR_NAMESPACE.
Return its hostname, TLS termination type, target Service, and target port.
Then get the endpoints for Service parksmap in that namespace and return the pod IPs and their readiness.
Identify the tools you used and the resources they queried.
Do not modify resources, exec into pods, or read Secrets.
If you cannot reach live cluster data, say so.
----
+
If a tool approval appears, inspect the tool name, the namespace it targets, and the resource type. Approve only the Route and Service endpoint reads. Decline any request to read Secrets, exec into pods, or inspect other namespaces.

. Compare the AI response with the API output from Exercise 3:
+
[source,bash,role=execute]
----
oc get route parksmap -n "$LAB_NAMESPACE" \
  -o jsonpath='host={.spec.host}{"\n"}termination={.spec.tls.termination}{"\n"}service={.spec.to.name}{"\n"}'
oc get endpointslices.discovery.k8s.io \
  -l kubernetes.io/service-name=parksmap \
  -n "$LAB_NAMESPACE" \
  -o jsonpath='{range .items[*]}{range .endpoints[*]}{.addresses[0]}  ready={.conditions.ready}{"\n"}{end}{end}'
----
+
*Expected:* hostname, termination type, Service name, and ready endpoint IPs match between the AI response and the API output. A discrepancy means either the tool read stale data or the AI generated the answer from context rather than a live query.

NOTE: The tool name and resource path should appear in the AI response. A generic explanation of Routes without a named tool and resource is not evidence of live access.

=== CLI Evidence Path (AI Integration Not Available)

If the AI path is not configured, record *live access not verified* and complete the ingress evidence with the CLI:

[source,bash,role=execute]
----
oc describe route parksmap -n "$LAB_NAMESPACE" | \
  grep -E 'Host:|Labels:|TLS Termination:|Service:|Port:|Endpoint Port:'
oc get endpointslices.discovery.k8s.io \
  -l kubernetes.io/service-name=parksmap \
  -n "$LAB_NAMESPACE" -o wide
----

*Checkpoint:* You have either verified that configured AI tools read live Route and endpoint data from your namespace, or recorded that live access is not available in this environment. A chat explanation based on supplied data is not a live read.

== Exercise 5: Record the Workload Baseline (3 Minutes)

Observations from a healthy application become the reference point for Module 3 resource controls and Module 4 incident investigation. Capture them now while the application is known-good.

. Check current pod CPU and memory usage:
+
[source,bash,role=execute]
----
oc adm top pods -n "$LAB_NAMESPACE" \
  -l "$APP_SELECTOR" --containers
----
+
If this command returns a permissions error, open *Observe > Metrics* in the console, select your project, and run the query `container_memory_working_set_bytes{namespace="$LAB_NAMESPACE"}` instead. Record the result or explicitly note that metrics are unavailable.

. Check recent namespace events for warnings:
+
[source,bash,role=execute]
----
oc get events -n "$LAB_NAMESPACE" \
  --sort-by=.metadata.creationTimestamp \
  --field-selector reason!=Scheduled,reason!=Started,reason!=Pulled,reason!=Created \
  | tail -20
----
+
Events indicate restarts, image pull failures, or other warnings from earlier in the session. An empty list or only normal scheduling events confirms a clean baseline.

. Note the evidence directory for later reference:
+
[source,bash,role=execute]
----
printf 'Evidence directory: %s\n' "$MODULE01_EVIDENCE"
ls "$MODULE01_EVIDENCE/"
----

*Checkpoint:* You have CPU and memory observations for a healthy National Parks instance, or recorded that metrics are unavailable. These values are your reference for Modules 3 and 4.

== Optional Tour: Ingress Behaviour or Extension Inspection (5–10 Minutes)

Choose one option your instructor has enabled.

=== Option A: Inspect a HAProxy Request-Validation Change

The {ocp5-release-notes}#ocp-release-notes-networking_release-notes[release notes] describe HAProxy 3.2.22 as the new default and note changes to request validation and some HTTP error responses. Verify normal behaviour first.

. Confirm the frontend still returns a normal response:
+
[source,bash,role=execute]
----
curl --fail --silent --show-error --connect-timeout 5 --max-time 15 \
  -o /dev/null -w 'status=%{http_code}\n' \
  "$PARKSMAP_URL/"
----
+
*Expected:* `status=200`.

. Send a request with a double-slash path target to your own frontend Route and observe the response code:
+
[source,bash,role=execute]
----
curl --path-as-is --silent --show-error --connect-timeout 5 --max-time 15 \
  -o /dev/null -w 'status=%{http_code}\n' \
  "${PARKSMAP_URL}/ws//double-slash"
----
+
Compare the response code with the behaviour documented in the release notes for HAProxy 3.2. Your instructor will confirm which router version admits this Route and whether any external proxy affects the result.

NOTE: Do not change IngressController configuration or send requests to Routes in other students' namespaces.

=== Option B: Inspect an Installed Extension

. List cluster extensions:
+
[source,bash,role=execute]
----
oc get clusterextension -o wide 2>/dev/null || \
  printf '%s\n' 'ClusterExtension API not found on this cluster.'
----

. For each extension providing a workshop capability, record its installed version and reported health. Ask the instructor to confirm support status for the installed version against this OpenShift build.

NOTE: OLM v1 and the `ClusterExtension` API predate OpenShift 5. Check each extension's own release notes and support status independently.

== Troubleshooting

[cols="2,3",options="header"]
|===
| Symptom | Next step
| `oc` not authenticated | Use *Copy login command* from your console user menu. Keep the token out of AI prompts.
| Namespace variable unset | Re-run the `read` command in Exercise 1 step 3 in the same terminal session.
| `Forbidden` on any resource | Run `oc whoami` to confirm your identity, then ask the instructor to check the namespace RoleBinding.
| A Deployment is not Ready | Run `oc describe deployment/<name> -n "$LAB_NAMESPACE"` and check the Events section. This is a setup issue.
| Frontend returns non-200 | Check pod logs and events. A Route with no ready endpoints returns `503`.
| Backend health endpoint fails | Check backend pod logs. A connectivity failure to the Route is different from an application error.
| Data endpoint returns empty or errors | The database is likely not initialized. Ask the instructor to reload. Do not call `/ws/data/load` yourself during the timed session.
| MCP tool approval does not appear | The AI integration is likely not connected. Record live access as unavailable and use the CLI path.
| `oc adm top` returns Forbidden | Use the console *Observe > Metrics* view. Record explicitly if metrics data is unavailable.
| Shell variables lost | Variables do not persist across terminal sessions. Re-run the setup steps from Exercise 1.
|===
