= Operating Applications on OpenShift 5: Platform Engineering, AI & GitOps
:navtitle: Lab Overview

Work through the day-to-day responsibilities of a platform engineer: discover your environment, onboard an application, apply tenant and resource controls, investigate an incident, and deliver a verified fix through GitOps.

The workshop is designed for up to 30 participants on a shared OpenShift cluster. You use your own student account and assigned namespace. Module 1 starts with hands-on discovery and an evidence check: can OpenShift Lightspeed retrieve a fresh value from a resource you created, and can you verify the answer with `oc`?

[NOTE]
====
*This workshop is being developed module by module.* Module 1 contains the first hands-on guide. Modules 2–5 show the planned learning path below; their exercises are not yet complete.

The configured platform target is *{ocp_version}*. The https://rhpds.github.io/ocp5-ea-showroom/modules/index.html[OpenShift 5 Early Access reference] describes an evaluation environment with additional components. Verify the actual cluster release, feature configuration and your permissions in Module 1. A target version does not establish that every preview feature is installed or generally available.
====

== What You Will Do

* Inspect your identity, namespace, running release and available platform APIs.
* Create a small test resource and compare a Lightspeed/MCP response with the Kubernetes API.
* Distinguish verified live access from an AI explanation based on data you supplied.
* Continue, as the later modules are completed, into application onboarding, tenant isolation, resource controls, incident investigation and GitOps remediation.

The later exercises will use familiar OpenShift foundations—GitOps, RBAC, NetworkPolicy, ResourceQuota and LimitRange—alongside the early-access capabilities available in the workshop environment. These foundations are not presented as new OpenShift 5 features.

== OpenShift 5 Early-Access Topics

Module 1 introduces the following areas from the reference material and helps you identify what is available in your environment:

[cols="2,3",options="header"]
|===
| Topic | What you will look for
| Agentic troubleshooting | User-initiated investigations, alert-initiated runs, evidence and configured approval stages.
| OpenShift MCP server | Tools that allow an AI client to retrieve platform data within the integration's effective permissions.
| Perses charts | Metrics-backed visualisations in Lightspeed and the observability console, where configured.
| MCP Gateway | Federation, authentication, tool authorisation and rate limiting through Red Hat Connectivity Link.
| Advanced Cluster Security 5 | VM vulnerability scanning, file activity monitoring, init container coverage and ACS MCP integration.
| AI-assisted update assessment | The distinction between agentic upgrade analysis and user-initiated Lightspeed assessments; instructor demonstration only.
|===

Connectivity Link and Advanced Cluster Security are additional products with their own installation and configuration requirements. Preview availability and support status must be checked for each installed component. The workshop does not assume that the reference environment's cluster-admin exercises are suitable for a shared student cluster.

== Your Environment

[cols="2,4",options="header"]
|===
| Component | What to confirm before use

| OpenShift console and CLI
| Your instructor supplies the real console URL, student credentials and a terminal with a compatible `oc` CLI. Module 1 checks the active account and cluster endpoint.

| Assigned namespace
| A pre-created namespace and scoped permissions are required for Module 1. You create one ConfigMap there; network and access isolation are subjects for Module 2 to verify.

| OpenShift Lightspeed and MCP
| The live-read exercise requires a working model connection, configured MCP integration and permission to read your test resource. If live tools are unavailable, the guide includes a clearly labelled supplied-data fallback.

| OpenShift GitOps (Argo CD)
| Required for the planned onboarding and remediation modules. Your instructor will confirm your assigned Argo CD instance, Git repository, credentials and permitted deployment destinations before Module 2.

| Metrics and optional console plugins
| Availability depends on monitoring configuration, plugin installation and your account permissions. Module 1 provides a conditional metrics/Perses tour.

| Connectivity Link, ACS and agentic components
| Optional for the feature tours. Your instructor identifies the permitted views or demonstrates them; students do not reconfigure shared platform services.

| Sample application
| Application onboarding is planned for Module 2. Module 1 does not require the application to be deployed and does not inject a fault.
|===

== Before You Start

This workshop is intended for intermediate platform engineers and site reliability engineers. You should be comfortable with:

* Pods, deployments, namespaces and basic RBAC.
* Running basic `oc` commands in a Bash terminal.
* Cloning a Git repository, committing changes and pushing a branch for the later modules.

Have your console URL, student credentials and assigned namespace ready. Use your student account in both the console and terminal. Keep credentials and tokens out of AI prompts and workshop notes; the Module 1 exercise uses synthetic data.

The guide includes observable checkpoints and troubleshooting steps. If a preview component is missing, record that result and use the documented alternative. Completion means you can explain what you verified and what remains unavailable—not that every feature in the reference must appear on your cluster.
