= Operating Applications on OpenShift 5: Platform Engineering, AI & GitOps
:navtitle: Lab Overview

Work through the responsibilities of a platform engineer: establish an application baseline, understand GitOps, apply tenant and resource controls, investigate an incident, and deliver a verified fix.

Module 1 uses *National Parks*, the application described in the OpenShift 5 Tutorials guide. You will open the map, check a database-backed response, trace the application's ingress path, and compare AI findings with current cluster evidence.

The workshop is designed for up to 30 participants on a shared OpenShift cluster. Each participant uses an assigned identity and application namespace.

== What You Will Do

* Identify the frontend, backend, and database in `national-parks-app`.
* Verify the map, its HTTP responses, and a read of the park dataset.
* Follow a Route through its Service and EndpointSlices to the current application pods.
* Use configured MCP inspection tools to investigate the ingress path, or complete the CLI evidence path when the integration is unavailable.
* Record workload metrics and logs as an operational baseline.
* Continue into the GitOps, access control, resource management, and incident investigation drafts using the same application.

The guide distinguishes documented OpenShift 5 changes from existing foundations such as Deployments, Routes, GitOps, RBAC, and NetworkPolicy.

== Release Topics Connected to the Application

[cols="2,3",options="header"]
|===
| Topic | Workshop connection
| Kubernetes and runtime foundation | Compare the actual platform release with the documented Kubernetes 1.36 / CRI-O foundation for OpenShift 5.0.
| MCP server — GA in 5.0 | Verify live resource reads for the application's Route, Service, EndpointSlices, and a pod UID. `netedge` adds an optional, explicitly enabled inspection exercise.

== Before You Start

This workshop is intended for intermediate platform engineers and site reliability engineers. You should be comfortable with pods, Deployments, namespaces, basic RBAC, and running `oc` commands. Later exercises also require basic Git operations.

Your application namespace and console username are `{lab_user}`. The terminal can authenticate as the corresponding Showroom service account; its hosting namespace can differ from the application namespace. Keep credentials out of AI prompts and notes.

Module 1 uses a healthy, pre-provisioned application. Database initialization and image builds are instructor preparation, outside the timed lab. The module includes observable checkpoints and does not inject an application fault.
