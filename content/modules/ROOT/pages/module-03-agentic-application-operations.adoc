Use your assigned `{user}` credentials. Do not share passwords or reuse this disposable workshop password.

In Modules 1 and 2 you deployed two healthy National Parks stacks. Now operate them as a platform engineer: distinguish *resource usage* from *requests, limits and quota*, and make an evidence-based, source-controlled adjustment to ParksMap. This replaces the former duplicate readiness-probe incident; the single readiness incident now lives in Module 4.

*Estimated time: 25 minutes* (five missions). No additional operator installation, cluster-wide quota change, PriorityClass or AgenticRun is required of students.

[IMPORTANT]
.Scope and safety
====
The *existing* shared ClusterResourceQuota and LimitRange belong to tenant provisioning. Students must not create or modify either, nor modify PriorityClasses, PVCs, Secrets, Argo CD controller resources or other students' namespaces. Never edit the GitOps-managed Deployment directly. No stress-test Pods or forced contention are needed on the shared cluster.

Student AgenticRuns remain *deferred* because cross-namespace sandbox behavior and tenant isolation are unresolved. Use normal console metrics, Lightspeed read-only analysis when available, and namespaced CLI evidence.
====

== Mission 1: Inspect your baseline and resource commitments (4 minutes)

. Establish namespaced CLI context and verify that both National Parks stacks are healthy:
+
[source,bash,subs="attributes+",role=execute]
----
STUDENT={user}
export LAB_NAMESPACE="$STUDENT-demo"
export GITOPS_NAMESPACE="$STUDENT-gitops"
export ARGOCD_NAMESPACE="$STUDENT-gitops"
export ARGOCD_APP=national-parks-settings
oc get deployments -n "$LAB_NAMESPACE"
oc get deployments -n "$GITOPS_NAMESPACE"
oc get application "$ARGOCD_APP" -n "$ARGOCD_NAMESPACE" -o json | jq -r   '[.status.sync.status,.status.health.status] | join(" / ")'
----
+
Do not continue if ParksMap, the Python backend or MongoDB is unhealthy.

. Inspect only resource settings on the GitOps-managed ParksMap Deployment:
+
[source,bash,subs="attributes+",role=execute]
----
oc get deployment parksmap -n "$GITOPS_NAMESPACE" -o json | jq   '.spec.template.spec.containers[0] | {name,image,resources,readinessProbe}'
oc get limitranges -n "$GITOPS_NAMESPACE"
----
+
The canonical workspace currently requests *75m CPU and 192Mi memory*, with limits of *500m CPU and 768Mi memory* for ParksMap. These are scheduling and enforcement values, *not* measured utilization.

== Mission 2: Inspect real CPU and memory evidence (5 minutes)

. In OpenShift 5 select *Observe → Dashboards (Perses)*. Select *your own* +$GITOPS_NAMESPACE+ project, then the instructor-provisioned dashboard *OpenShift 5 | National Parks & WeatherNow* (+PersesDashboard/workshop-workloads+). Set the time range to *Last 1 hour* and identify ParksMap CPU, memory working set, restart and readiness panels. This dashboard can only be used after the instructor has verified its datasource cannot query another student’s metrics.
+
[source,bash,subs="attributes+",role=execute]
----
oc get persesdashboard workshop-workloads -n "$GITOPS_NAMESPACE" || echo "Perses dashboard not provisioned; use Observe > Metrics."
oc get persesdatasource workshop-workloads -n "$GITOPS_NAMESPACE" || echo "Tenant datasource unavailable; do not use operator accelerators datasource."
----
+
If either resource is unavailable, *do not create datasources or copy monitoring Secrets*. Use *Observe → Metrics* or the namespaced CLI and record Perses as not configured. The built-in *Application Performance Monitoring (APM)* dashboard is not a substitute for workload CPU/memory metrics from this application. If the dashboard says *No data*, verify time range and project; missing data does not mean usage is zero.
+
. If Perses shows *No dashboards found*, open *Observe → Metrics*, choose your GitOps project and run each of these queries over the same time range. Read the CPU result in cores and the memory result in MiB. Record two readings at different times.
+
[source,text,subs="attributes+",role=copypaste]
----
sum by (pod) (rate(container_cpu_usage_seconds_total{namespace="{user}-gitops",container="parksmap"}[5m]))
----
+
[source,text,subs="attributes+",role=copypaste]
----
max by (pod) (container_memory_working_set_bytes{namespace="{user}-gitops",container="parksmap"}) / 1048576
----

. Read current sampled usage as a second source:
+
[source,bash,subs="attributes+",role=execute]
----
oc adm top pods -n "$GITOPS_NAMESPACE" --containers ||   echo "Metrics unavailable to this identity; record the limitation and use the console."
oc get pods -n "$GITOPS_NAMESPACE" -o wide
oc get deployment parksmap -n "$GITOPS_NAMESPACE" -o jsonpath='{.status.readyReplicas}{" Ready of "}{.spec.replicas}{" desired\n"}'
----
+
If metrics are missing, do *not* infer resource usage from limits or invent a utilization figure. Ask the instructor for a pre-captured, namespace-scoped metrics example. Only make a tuning change based on trustworthy observations.

== Mission 3: Assess shared quota headroom (5 minutes)

. Inspect the existing namespace-scoped view of the shared tenant quota:
+
[source,bash,subs="attributes+",role=execute]
----
if [ "$(oc auth can-i get appliedclusterresourcequotas.quota.openshift.io -n "$GITOPS_NAMESPACE")" = yes ]; then
  oc describe appliedclusterresourcequota "tenant-$STUDENT" -n "$GITOPS_NAMESPACE" ||     echo "Applied quota object not visible; ask your instructor."
else
  echo "Quota visibility is restricted; instructor supplies a sanitized headroom snapshot."
fi
oc describe deployment parksmap -n "$GITOPS_NAMESPACE"
----
+
Do not add quota figures from +$LAB_NAMESPACE+ and +$GITOPS_NAMESPACE+: they are two views of the same tenant allocation. Rollout surge can briefly require extra requests and limits because old and replacement Pods coexist.

. Try the quota admission decision without scheduling a Pod. One small request should fit. The second requests the tenant's entire CPU-request allocation while other workloads already hold part of it. The server checks both dry runs against the same live quota.
+
[source,bash,subs="attributes+",role=execute]
----
quota_trial() {
  oc create --dry-run=server -n "$GITOPS_NAMESPACE" -f - -o name <<YAML
apiVersion: v1
kind: Pod
metadata:
  generateName: sizing-check-
spec:
  restartPolicy: Never
  containers:
  - name: sample
    image: quay.io/openshift-workshop-applications/weathernow:latest
    resources:
      requests: {cpu: "$1", memory: 32Mi}
      limits: {cpu: "$1", memory: 128Mi}
YAML
}
CPU_CAP=$(oc get appliedclusterresourcequota "tenant-$STUDENT" -n "$GITOPS_NAMESPACE" \
  -o json | jq -er '.spec.quota.hard["requests.cpu"] // .status.total.hard["requests.cpu"]') &&
  quota_trial 25m && quota_trial "$CPU_CAP"
----
+
Record the small Pod's dry-run name and the second admission response. A quota rejection must name the exceeded quota and identify requested, used and allowed resources. If a LimitRange, missing permission or unavailable quota stops the check, record that cause and have the instructor verify a usable quota example. Neither dry run consumes capacity. Compare the available headroom with the extra Pod that a rolling update may need.
+
If you use only the console, open *Search* in `{user}-gitops`, select `AppliedClusterResourceQuota` and inspect `tenant-{user}` for used and hard values. Record the available capacity. Leave both admission checks pending until you have the two server responses from a terminal signed in as `{user}`.

. Decide whether a resource change is justified. Use this *bounded training decision table*, not a guessed production recommendation:
+
[cols="2,3",options="header"]
|===
| Observation | Allowed GitOps action
| Sustained low CPU usage with no bursts | Consider ParksMap CPU request *75m → 50m*
| Sustained demand above 75m or repeated CPU-related pressure | Consider CPU request *75m → 100m*
| Memory working set repeatedly near or above 192Mi | Consider memory request *192Mi → 256Mi*
| Data inconclusive or already well sized | Keep the existing requests; record *no change justified*
|===
+
These are intentionally narrow options for a disposable lab. Do not lower memory requests below 192Mi, raise CPU above 100m, or change the 500m CPU / 768Mi memory limits. The instructor must verify shared-quota headroom before any higher request, especially for a rolling update.

*Checkpoint 3:* Write down your observation, the selected request value (including a justified *no change*), and how rolling-update surge affects quota.

== Mission 4: Make a safe GitOps sizing change (7 minutes)

. In *your own Gitea main branch* open +national-parks/04-parksmap-frontend.yaml+ and locate:
+
[source,yaml,role=copypaste]
----
resources:
  requests:
    cpu: 75m
    memory: 192Mi
  limits:
    cpu: 500m
    memory: 768Mi
----
+
Modify only the supported request field if the measurement supports the adjustment. Do *not* change the image, readiness port (+http+), Service, RBAC or database. Keep the limits shown above. If the data does not justify any change, document *no change* and proceed to Mission 5; this is a valid real-world sizing decision.
. Commit any selected adjustment using:
+
[source,text,role=copypaste]
----
tune(module03): adjust ParksMap resources from observed usage
----
+
. Verify that Auto-Sync, not an +oc patch+, updates the Deployment:
+
[source,bash,subs="attributes+",role=execute]
----
curl -fsSLo check-release.py "https://showroom-{user}-showroom.{openshift_cluster_ingress_domain}/www/modules/_attachments/check-release.py" &&
python3 check-release.py {user} national-parks-settings synced &&
oc rollout status deployment/parksmap -n "$GITOPS_NAMESPACE" --timeout=180s
oc get deployment parksmap -n "$GITOPS_NAMESPACE" -o json | jq '.spec.template.spec.containers[0].resources'
----
+
If the rollout becomes blocked by quota, do not raise quota or delete other workloads. Restore the last known-good request values through Gitea and ask the instructor to review the shared allocation.

*Checkpoint 4:* Show either a justified Git commit and live request change, *or* recorded evidence explaining why no adjustment was safe.

== Mission 5: Confirm health and explain the decision (4 minutes)

. Verify your change did not affect application connectivity or the original National Parks deployment:
+
[source,bash,subs="attributes+",role=execute]
----
oc get deployments parksmap nationalparks mongodb-nationalparks -n "$GITOPS_NAMESPACE"
oc get deployments parksmap nationalparks mongodb-nationalparks -n "$LAB_NAMESPACE"
oc get application "$ARGOCD_APP" -n "$ARGOCD_NAMESPACE" -o json | jq   '{sync:.status.sync.status,health:.status.health.status,revision:.status.sync.revision}'
MAP_HOST="$(oc get route parksmap -n "$GITOPS_NAMESPACE" -o jsonpath='{.spec.host}')"
curl -sS -o /dev/null -w 'ParksMap HTTP %\{http_code}\n' "https://$MAP_HOST/"
----
+
You need a completed rollout, *Synced / Healthy* Argo CD application, functioning Route and healthy original namespace before proceeding.

== Troubleshooting

[cols="2,3",options="header"]
|===
| Symptom | Action
| Metrics unavailable | Record limitation, use instructor's tenant-scoped dashboard snapshot; do not guess usage
| Perses dashboard missing | Use OpenShift native Observe → Metrics or +oc adm top+; ask instructor to check COO preflight
| AppliedClusterResourceQuota forbidden | Instructor checks actual shared quota; students must not request cluster-admin
| Rollout blocked after tuning | Restore previous Git values; inspect quota and Pod Events
| Argo CD is Synced but health is degraded | Check the Deployment and Events; do not equate Sync with readiness
| Gitea workspace missing or stale | Instructor repairs the import/synchronization; don't create a replacement student repository
| AgenticRuns unavailable | Expected; no AgenticRun is required in this module
|===
